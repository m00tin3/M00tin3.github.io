第一节 专业技能八股

1.1 Java 基础

1.1.1 集合框架

Q1：Java 集合的整体体系是什么样的？
一句话结论：两大体系——Collection 和 Map；Collection 下面分 List、Set、Queue。

  • Collection：单列集合。
    • List（有序、可重复、有下标）：ArrayList（数组，查快改慢）、LinkedList（双向链表，改快查慢）、Vector（线程安全但已淘汰）、CopyOnWriteArrayList（写时复制，读多写少）。
    • Set（不重复）：HashSet（哈希表，无序）、LinkedHashSet（哈希表 + 双向链表，记录插入顺序）、TreeSet（红黑树，可排序）。
    • Queue：LinkedList、ArrayDeque、各种 BlockingQueue。
  • Map：双列集合，存 key-value。HashMap（数组+链表+红黑树）、LinkedHashMap（额外维护双向链表记录插入/访问顺序，可以做 LRU）、Hashtable（全部方法 synchronized，已淘汰）、TreeMap（红黑树，按 key 排序）、ConcurrentHashMap（线程安全）。

Q2：ArrayList 和 LinkedList 的区别？
一句话结论：ArrayList 是数组（随机访问 O(1)、中间增删 O(n)），LinkedList 是双向链表（随机访问 O(n)、增删 O(1)）。

  • 底层结构：ArrayList 用 Object[] elementData；LinkedList 用 Node<E>（prev + item + next）。
  • 复杂度：ArrayList 按下标访问 **O(1)**，中间插入删除要移动元素 **O(n)**；LinkedList 头尾增删 **O(1)**，按下标定位 **O(n)**（要先遍历）。
  • 内存：ArrayList 会有预留容量（扩容后可能有空洞）；LinkedList 每个节点多存两个指针，内存开销更大。
  • 实际项目里绝大多数场景用 ArrayList——数组的 CPU 缓存局部性好，即使中间增删，元素移动是连续内存操作，实测通常还是比 LinkedList 快。

Q3：ArrayList 的扩容机制？
一句话结论：默认容量 10，扩容为原来的 1.5 倍（oldCapacity + (oldCapacity >> 1)），扩容时用 Arrays.copyOf 复制到新数组。

  • 无参构造时 elementData 是空数组，第一次 add 才分配容量 10（懒加载）。
  • 扩容判断在 add 里：size == elementData.length 才扩容。
  • 1.5 倍是时间和空间的折中——扩太少会频繁拷贝，扩太多浪费内存。
  • 优化点：如果能预估元素个数，new ArrayList<>(容量) 一次到位，避免多次扩容拷贝。

Q4：HashMap 的底层结构（JDK 1.7 和 1.8 的差别）？
一句话结论：1.7 是「数组 + 链表」用头插法；1.8 改成「数组 + 链表 + 红黑树」，链表用尾插法，长度超过 8 且数组长度 ≥ 64 时转红黑树。

  • 数组叫 table（桶数组），每个桶里是一个链表或红黑树。
  • 1.8 引入红黑树的原因：哈希冲突严重时链表退化成 O(n) 查询，红黑树把最坏情况优化到 **O(log n)**。
  • 树化的两个条件必须同时满足：链表长度 > 8 且 table 长度 ≥ 64；不满足 64 时优先扩容而不是树化。
  • 退化条件：红黑树节点数 < 6 时退化为链表。8 和 6 之间留一个缓冲，避免在临界点反复转换。
  • 1.7 头插法在并发扩容时可能形成环形链表导致死循环；1.8 改尾插法解决了这个问题，但 HashMap 依然不是线程安全的（并发 put 仍可能丢数据）。

Q5：HashMap 的 put 过程？
一句话结论：算 hash 定位桶 → 桶空直接插 → 桶非空就比 hash 和 equals，相同则覆盖、不同则挂到链表/红黑树 → ++size > threshold 触发扩容。

  1. 计算 key 的 hash：(h = key.hashCode()) ^ (h >>> 16) —— 让高 16 位也参与运算，减少冲突。
  2. 如果 table 为 null 或长度为 0，先 resize() 初始化。
  3. (n - 1) & hash 定位桶下标（n 是数组长度，等价于对 n 取模但更快）。
  4. 桶为空：直接 new Node 放进去。
  5. 桶非空：先比 hash，再比 == 或 equals。相同就覆盖 value 并返回旧值；不同就遍历链表，尾插；链表长度达到 8 且 table ≥ 64 就树化。
  6. ++size > threshold（容量 × 0.75）就扩容成 2 倍。

Q6：HashMap 的容量为什么必须是 2 的 n 次方？负载因子为什么是 0.75？
一句话结论：2 的 n 次方是为了用位运算代替取模，并且让扩容后元素「要么原位、要么原位+oldCap」，不用重新算 hash；0.75 是空间和冲突概率的折中。

  • (n - 1) & hash 只有在 n 是 2 的幂时才等价于 hash % n——因为此时 n-1 的二进制全是低位 1，与运算正好取到低位，而 n 不是 2 的幂时低位有 0，会造成大量桶永远命中不到。
  • 扩容时（n → 2n），元素的新位置只取决于 hash 值新增的那一个 bit：是 0 就留在原下标，是 1 就移动到「原下标 + oldCap」。这就是 1.8 的 resize 不用重算 hash 的原因。
  • 负载因子 0.75 的权衡：太小（如 0.5）数组用不满就扩容，浪费空间且扩容频繁；太大（如 1.0）冲突概率上升，链表变长查询变慢。0.75 是泊松分布下的经验值。

Q7：为什么 HashMap 是线程不安全的？
一句话结论：多线程 put 会覆盖丢数据；1.7 还有并发扩容形成环形链表导致死循环的问题。

  • 丢数据：两个线程同时判断某个桶为空，都执行了插入，后一个会覆盖前一个。
  • size 不准：++size 不是原子操作（读-改-写三步），并发下会少加。
  • 1.7 死循环：头插法 + 并发扩容，两个线程同时改链表指针方向，可能形成环，之后 get 会一直循环。
  • 1.8 改尾插法避免了死循环，但丢数据和 size 不准依然存在，所以结论不变：HashMap 不能用于并发场景。

Q8：ConcurrentHashMap 是怎么实现线程安全的？
一句话结论：1.7 用分段锁（Segment 继承 ReentrantLock），1.8 去掉分段锁，改成「CAS 插空桶 + synchronized 锁桶的头节点」，锁粒度更细。

  • 1.7：整个容器是一个 Segment[]，每个 Segment 里是一个「数组 + 链表」，继承 ReentrantLock。默认 16 个 Segment，理论上支持 16 个线程并发写。缺点是 Segment 数量一旦初始化不能扩容。
  • 1.8：结构变成和 HashMap 一样（数组 + 链表 + 红黑树），并发控制分两种情况：
    • 桶为空：用 CAS 直接把新节点放进桶，不加锁，这是最乐观的路径。
    • 桶非空：用 synchronized 锁住这个桶的头节点，只锁一个桶，不是锁整个表。
    • 初始化 table、扩容时用 CAS + 自旋 + 多线程协助迁移（transfer 时用 ForwardingNode 标记）。
  • 为什么用了 synchronized 还要用 CAS：无冲突时 CAS 一次成功，省掉加锁解锁的开销，性能最好；有冲突时 synchronized 更合适，因为此时自旋会白白消耗 CPU。两者是「快路径 + 慢路径」的配合，不是二选一。
  • 补充：ConcurrentHashMap 不允许 null key 和 null value——因为并发下 get 返回 null 无法区分「key 不存在」还是「value 就是 null」，这在并发场景里是致命的歧义。

Q9：CopyOnWriteArrayList 的原理和适用场景？
一句话结论：写时复制——写操作先加锁、复制出一个新数组、改完再替换引用；读操作不加锁。适合读多写极少的场景。

  • 底层是 volatile transient Object[] array。volatile 保证数组引用一改，其他线程立刻可见。
  • 写流程（add/set/remove）：加 ReentrantLock → Arrays.copyOf 复制新数组 → 在新数组上改 → setArray 替换引用 → 解锁。整个写操作全程不影响读。
  • 读流程（get）：直接读当前数组引用，不加锁。
  • 优点：读写完全分离，读操作无锁，不会有 ConcurrentModificationException（迭代器拿到的是快照）。
  • 缺点：① 内存开销大——每次写都复制整个数组，数组大时很浪费；② 数据弱一致——写的瞬间，别的线程读到的还是旧数组；③ 写性能差。
  • 适用场景：读远多于写、数据量小。典型是监听器列表、配置白名单。项目里发帖防重的场景不用它，因为那是 Redis 的活。

Q10：HashMap 和 Hashtable 的区别？
一句话结论：HashMap 线程不安全、允许 null、默认容量 16、扩容 2 倍；Hashtable 方法全 synchronized、不允许 null、默认容量 11、扩容 2n+1。现在用 Hashtable 不如用 ConcurrentHashMap。

  • 继承关系：Hashtable 继承 Dictionary（已废弃）；HashMap 继承 AbstractMap。
  • 并发：Hashtable 用 synchronized 锁整个表，并发性能差；ConcurrentHashMap 锁粒度细，是替代品。
  • null：HashMap 允许一个 null key（hash 值直接当 0）和多个 null value；Hashtable 直接抛 NPE。

1.1.2 泛型

Q1：什么是泛型？为什么需要泛型？
一句话结论：泛型就是「把类型也当成参数传」；好处是编译期就能发现类型错误，并且省掉强制类型转换。

  • 没有泛型的时候，集合里存的是 Object，取出来必须强转，类型错了要等到运行期才抛 ClassCastException。
  • 有了泛型：List<String> 编译器就替你保证放进去和取出来的都是 String，类型错误在编译期就报错，而且不用写 (String) 强转。
  • 一句话记法：把类型检查从运行期提前到编译期。

Q2：泛型有哪几种写法？
一句话结论：三种——泛型类、泛型方法、泛型接口。

  • 类型参数名字只是约定：T = Type、E = Element、K = Key、V = Value、? = 通配符，都不是关键字，写成 A、B 也能编译。
  • 项目里用得最多的是统一返回体 Result<T>（包 OrderVO、EmployeeLoginVO）、MyBatis-Plus 的 BaseMapper<T>、OpenFeign 的接口返回值。

Q3：泛型的上下界是什么？PECS 是什么意思？
一句话结论：? extends T 是上界（只能读，不能写）；? super T 是下界（可以写，读出来只能当 Object）；记法是 PECS——Producer Extends, Consumer Super。

  • 为什么上界不能写：编译器不知道 producer 到底是 List<Integer> 还是 List<Double>。如果是后者，你写一个 Integer 进去就破坏了类型安全。所以干脆禁止写（除了写 null）。
  • 记法：你从这个集合里往外取数据（它是生产者），用 extends；你往里放数据（它是消费者），用 super。
  • 这个规则不是死记的，JDK 源码里到处都是例子，比如 Collections.copy(List<? super T> dest, List<? extends T> src)——src 是生产者用 extends，dest 是消费者用 super。

Q4：什么是类型擦除？它带来了哪些限制？
一句话结论：泛型只在编译期存在，编译完所有泛型信息都被擦掉——无界的 T 擦成 Object，T extends Number 擦成 Number，运行时的 JVM 里没有泛型这个概念。

正因为擦除，才有下面这一串看起来奇怪、但一到面试就会问的限制：

限制 原因
不能 new T() 运行时不知道 T 是什么，没法调构造器
不能 new T[] / new ArrayList<T>[10] 数组是运行时检查元素类型的，虚拟机不知道要检查什么
不能 instanceof List<String> 运行时只有一个 List，List<String> 这个类型不存在
静态方法里不能用类的类型参数 静态成员属于类不属于实例，而类型参数是实例级的
不能用 List<int>，只能用 List<Integer> 泛型不支持基本类型；擦除后 T 要擦成 Object，而基本类型不是 Object
两个方法的类型参数擦除后签名相同就冲突 如 void f(List<String>) 和 void f(List<Integer>) 擦除后都是 void f(List)，编译报错
  • 一句话总结：泛型是编译器给你的语法糖和类型检查，字节码里什么都没有。

1.1.3 异常处理

Q1：Java 的异常体系？
一句话结论：根是 Throwable，分两支——Error（程序处理不了的严重问题）和 Exception（程序可以处理的）；Exception 又分受检和非受检。

Q2：受检异常和非受检异常的区别？实际怎么用？
一句话结论：受检异常必须 try-catch 或往上 throws（编译期强制）；非受检异常编译器不管，通常是代码写错了。

  • 受检异常：继承 Exception 但不继承 RuntimeException。编译器强制你处理。设计意图是「这个异常是可恢复的、调用方应该知道」——比如 IOException 表示文件读不到，调用方可以重试或换文件。
  • 非受检异常：继承 RuntimeException。设计意图是「这是编程错误，靠改代码解决，不是靠捕获」——比如空指针、数组越界、参数非法。
  • Spring 里的一条重要规则：**@Transactional 默认只对 RuntimeException 和 Error 回滚**。如果抛的是受检异常想让它回滚，必须写 @Transactional(rollbackFor = Exception.class)。这条是事务失效里最常被问的一条。

Q3：try-catch-finally 的执行顺序？try{return "a"} finally{return "b"} 返回什么？
一句话结论：返回 “b”。finally 里的 return 会覆盖 try 里的 return。

  • 正常流程：try 执行完 → finally 执行完 → 才真正 return。try 里的 return 值会先被暂存，finally 执行完再用暂存值返回，所以 finally 里改局部变量不影响返回值。
  • 但 finally 里如果也有 return，直接覆盖，所以返回 “b”。
  • 结论：finally 里绝对不要写 return，它会吞掉异常、覆盖返回值，是典型的藏 bug 写法。finally 只该用来释放资源。
  • 补充：finally 一定执行吗？几乎一定，但有两个例外——System.exit() 直接退 JVM；线程被 kill 掉。

Q4：项目中异常是怎么处理的？
一句话记法：全局异常处理器 + 自定义业务异常 + 统一返回体，三层配合。

  • 自定义业务异常：继承 RuntimeException（因为是非受检，不用到处 throws）。比如 BusinessException，带 code 和 msg，提供静态工厂方法 BusinessException.seckill(4002, "手慢了")。
  • 全局异常处理器：用 @RestControllerAdvice + @ExceptionHandler 统一拦截，把异常翻译成统一返回体 Result.error(code, msg)，避免每个 Controller 都写 try-catch。
  • 兜底：再挂一个 @ExceptionHandler(Exception.class) 兜住所有没预料到的异常，返回「系统繁忙」并且打 error 日志（带堆栈），但不要把堆栈返给前端（泄露信息）。
  • 统一返回体：Result<T>{ code, msg, data }，code 用 1 表示成功（对齐前端约定），业务错误码分段管理（比如 4001~4004 是秒杀段）。
  • 一个原则：业务异常用 log.warn（是预期内的分支，不是故障），系统异常用 log.error（需要人去看）。

1.1.4 线程安全

Q1：线程安全要解决哪三个问题？
一句话结论：原子性、可见性、有序性——三个问题三个手段。

问题 是什么 怎么解决
原子性 一个或多个操作要么全做完，要么全不做（i++ 是读-改-写三步，不是原子的） synchronized、Lock、Atomic* 系列（CAS）
可见性 一个线程改了共享变量，另一个线程能不能立刻看到（因为 CPU 缓存/工作内存的存在，可能看不到） volatile、synchronized、Lock、final
有序性 编译器和 CPU 会做指令重排序（单线程语义不变，但多线程下可能出问题） volatile、synchronized、happens-before 规则
  • happens-before 是 JMM 的核心规则：只要满足 happens-before，前一个操作的结果对后一个操作可见。最常用的几条——程序顺序规则（同线程内前面的对后面的可见）、volatile 规则（写 volatile 变量的操作 happens-before 后续读它）、监视器锁规则（解锁 happens-before 后续加锁）、传递性。
  • Java 内存模型（JMM）：每个线程有自己的工作内存（对应 CPU 缓存/寄存器），共享变量存在主内存。线程读写变量时是「从主内存拷到工作内存、改完再写回」，所以才有可见性问题。volatile 的作用就是强制读写都走主内存。

Q2：synchronized 的原理？
一句话结论：字节码层面是 monitorenter / monitorexit 两条指令，依赖对象头里的 Mark Word 和操作系统互斥锁（mutex）。

  • 对象头结构：对象头里的 Mark Word 存哈希码、GC 分代年龄、锁状态标志。锁状态不同，Mark Word 存的东西不一样。
  • 同步代码块：编译后在代码块前后插入 monitorenter 和 monitorexit（会有两个 exit，一个正常路径、一个异常路径保证解锁）。
  • 同步方法：方法上打一个 ACC_SYNCHRONIZED 标志，JVM 隐式加锁。
  • 锁什么：锁普通方法锁的是 this；锁静态方法锁的是 Class 对象（全局唯一，所以所有实例共享同一把锁）。
  • 可重入怎么实现的：对象监视器里存「持有锁的线程 ID」和一个计数器。同一个线程再次加锁计数器 +1，释放时递减，减到 0 才真正释放。
  • 监视器有两个队列：entryList（等待获取锁的线程）和 waitSet（调用 wait() 后主动等待的线程）。

Q3：锁升级的过程？
一句话结论：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，只能升级不能降级，目的是在不同的竞争程度下用最便宜的方式实现互斥。

状态 触发条件 做了什么 开销
无锁 初始 Mark Word 存哈希码 —
偏向锁 只有一个线程访问 把线程 ID 记到 Mark Word，之后同一线程进出只比 ID，不做任何 CAS 几乎为零
轻量级锁 有第二个线程来竞争 用 CAS 把 Mark Word 复制到线程栈的 Lock Record（Displaced Mark Word），失败就自旋 CAS + 自旋
重量级锁 自旋超过一定次数还没拿到 线程被操作系统挂起（用户态→内核态切换） 最贵，但不用空转 CPU
  • 一句话记：偏向锁是「我一个人用，不用锁」；轻量级锁是「偶尔争一下，CAS 加点自旋就够」；重量级锁是「争得太凶，老老实实排队睡觉」。
  • JVM 还会做 锁消除（逃逸分析发现对象不逃逸，直接去掉同步）和 锁粗化（相邻的多次加锁合并成一次）。

Q4：volatile 的作用？
一句话结论：保证可见性和有序性，但不保证原子性。

  • 可见性：写 volatile 变量时立即刷回主内存，并且把其他线程工作内存里的副本置为无效；读的时候强制从主内存读。
  • 有序性：通过内存屏障禁止指令重排序。写操作前插 StoreStore 屏障、写后插 StoreLoad 屏障；读操作后插 LoadLoad 和 LoadStore 屏障。
  • 不保证原子性：volatile int i; i++ 依然是读-改-写三步，并发下会丢更新。要原子就得上 AtomicInteger（CAS）或加锁。

Q5：CAS 是什么？有什么问题？
一句话结论：CAS 是「比较并交换」，三个操作数——内存值 V、预期值 A、新值 B，只有 V == A 时才把 V 改成 B，靠 CPU 的 cmpxchg 指令保证原子。三个问题：ABA、自旋开销大、只能保证一个变量。

  • 为什么无锁还安全：比较和交换这一整套是硬件原子指令，中间不会被别的线程插进来。
  • 问题一：ABA。线程 1 读到 A，线程 2 把值从 A 改成 B 又改回 A，线程 1 再 CAS 依然成功，但它不知道中间变过。解决：加版本号，用 AtomicStampedReference，每次修改版本号 +1。
  • 问题二：自旋开销。CAS 失败会自旋重试，高并发下大量线程空转，白白烧 CPU。这就是为什么锁竞争激烈时 synchronized 反而更好。
  • 问题三：只能保证单个变量。多个变量要原子更新，得用 AtomicReference 打包成一个对象，或者直接加锁。
  • CAS 和 AQS 的关系：AQS 里那个 volatile int state 的修改就是靠 Unsafe.compareAndSwapInt 做的，CAS 是 AQS 的实现基础。

Q6：AQS 是什么？
一句话结论：AQS（AbstractQueuedSynchronizer）是构建锁和同步器的框架，核心是「一个 volatile 的 state + 一个 FIFO 双向队列 + 模板方法」。

  • 三大部分：
    1. **volatile int state**：同步状态。含义由子类定义——ReentrantLock 里表示重入次数，CountDownLatch 里表示剩余计数，Semaphore 里表示可用许可数。
    2. FIFO 双向等待队列：抢不到锁的线程包装成 Node 入队并 LockSupport.park() 挂起；前驱节点释放时 unpark 唤醒后继。
    3. 模板方法：acquire / release 是骨架（AQS 写好了），子类只需重写 tryAcquire / tryRelease 决定「什么情况算拿到锁」。
  • 谁在用：ReentrantLock、ReentrantReadWriteLock、CountDownLatch、Semaphore、CyclicBarrier。
  • ReentrantLock 的可重入：tryAcquire 里先判断 state 是不是 0——是 0 就 CAS 抢并把 state 置 1；不是 0 就判断「持有者是不是自己」，是自己就把 state +1。
  • 公平和非公平的区别就在 tryAcquire：非公平版直接 CAS 抢（可以插队）；公平版先调 hasQueuedPredecessors()，队列里有人排队就不抢了，老老实实去队尾。
  • 一个特例：**tryLock() 不遵守公平原则**，它永远走非公平逻辑。

Q7：ThreadLocal 的原理？为什么会内存泄漏？
一句话结论：每个 Thread 内部有一个 ThreadLocalMap，key 是 ThreadLocal 对象本身（弱引用），value 是你要存的值（强引用）；key 被 GC 回收后 value 还在，就泄漏了。解决办法是用完调 remove()。

  • 结构：Thread → threadLocals（ThreadLocalMap）→ Entry[]，Entry 的 key 是 ThreadLocal（弱引用）、value 是值（强引用）。
  • 为什么 key 用弱引用：如果 key 用强引用，ThreadLocal 对象本身也会被这个 Map 引用着，即使业务代码不再用它，也回收不掉。
  • 泄漏链路：ThreadLocal 没有外部强引用了 → 下一次 GC 时 key 被回收变成 null → 但 value 还被 Thread → ThreadLocalMap → Entry → value 这条强引用链持有 → 线程不结束（线程池里的线程几乎永不结束），value 就永远回收不掉。

Q8：线程池的七个参数和提交流程？
一句话结论：7 个参数 = 核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略；提交流程是「核心满了进队列，队列满了扩到最大，都满了走拒绝策略」。

提交流程（务必按顺序说）：

  1. 当前线程数 < corePoolSize → 直接创建核心线程执行。
  2. 否则 → 把任务丢进 workQueue 排队。
  3. 如果队列满了，且线程数 < maximumPoolSize → 创建非核心线程执行。
  4. 如果队列满了、线程数也到最大值了 → 触发拒绝策略。

注意这里有个反直觉的点：是先入队，队列满了才扩线程，不是先扩线程。所以如果你用了无界队列（LinkedBlockingQueue 默认容量 Integer.MAX_VALUE），maximumPoolSize 永远用不上，队列会一直堆积直到 OOM。

四种拒绝策略：

策略 行为
AbortPolicy（默认） 直接抛 RejectedExecutionException，业务能感知、不会静默丢任务
CallerRunsPolicy 让提交任务的线程自己执行，等于反向施压，提交方被拖慢，自然降低提交速度
DiscardPolicy 静默丢弃，什么都不做（最危险，任务悄悄没了）
DiscardOldestPolicy 丢掉队列里最老的（等最久的）那个，把新任务加进去

也可以实现 RejectedExecutionHandler 自定义，比如把被拒绝的任务暂存到 Redis，后面异步重试。

Q9：核心线程数怎么设置？
一句话结论：CPU 密集型设「核数 + 1」，IO 密集型设「核数 × 2」或更高；实际生产要先压测再定。

  • CPU 密集型（大量计算，比如加解密、复杂算法）：线程开太多反而增加上下文切换开销，设 核数 + 1（+1 是为了在一个线程偶发缺页中断时顶上）。
  • IO 密集型（大量等待网络、磁盘，比如调第三方接口、查数据库）：线程大部分时间在等，可以多开，设 核数 × 2，如果 IO 等待比例特别高可以更高。
  • 更精确的公式：线程数 = 核数 × (1 + 平均等待时间 / 平均计算时间)。
  • 生产建议：公式只是起点，真正的值是压测压出来的——观察 CPU 使用率、队列堆积、平均响应时间，找到吞吐量和延迟的平衡点。
  • 命名线程很重要：用 ThreadFactory 给线程起有意义的名字（如 order-async-1），线上出问题 jstack 一看就知道是谁。

Q10：项目里的异步落库用的什么线程池？为什么不用 Executors 快捷方法？
一句话结论：手写 ThreadPoolExecutor；不用 Executors 是因为它的几个快捷方法要么用无界队列要么无限建线程，都可能 OOM。

  • Executors.newFixedThreadPool(n) 和 newSingleThreadExecutor() 用的是 无界队列 LinkedBlockingQueue，任务堆积起来直接 OOM。
  • Executors.newCachedThreadPool() 的 maximumPoolSize 是 Integer.MAX_VALUE，等于无限建线程，能直接把系统资源耗尽。
  • 《阿里巴巴 Java 开发手册》明确禁止用 Executors 创建线程池，必须手动 new ThreadPoolExecutor(...)，把每个参数显式写出来。
  • 项目里对应的做法：秒杀落库用 @Async，但必须显式指定自己的线程池（@Async("seckillExecutor")）——原因见下一条 Q11。

Q11：@Async 有什么坑？
一句话结论：不指定线程池的话，@Async 默认用 SimpleAsyncTaskExecutor——它会为每个任务新建一个线程且不复用，高并发下疯狂创建线程直到 OOM。

  • 必须显式指定线程池：定义自己的 ThreadPoolTaskExecutor，再用 @Async("seckillExecutor") 指定。这样才有核心线程复用、有队列、有拒绝策略。
  • 拒绝策略为什么选 CallerRunsPolicy：落库是关键写操作——AbortPolicy 会抛异常（用户抢到了但订单没落库），DiscardPolicy 更是静默丢失。CallerRunsPolicy 让提交任务的线程自己执行，等于反向施压：异步池忙不过来时，就拖慢抢购接口的响应速度，宁可慢，也不能丢。
  • 两个同源的限制（和 @Transactional 一样，因为都靠代理生效）：@Async 方法必须是 public，而且不能在同一个类里被 this 调用。

1.1.5 JVM 内存结构

Q1：JVM 的运行时数据区有哪些？
一句话结论：线程共享的——堆、方法区（1.8 后叫元空间）；线程私有的——虚拟机栈、本地方法栈、程序计数器。

区域 线程 内容 会不会 OOM
堆 共享 几乎所有对象实例，GC 的主战场 会（Java heap space）
方法区 / 元空间 共享 类元信息、运行时常量池、静态变量、JIT 编译后的代码 会（Metaspace）
虚拟机栈 私有 每个方法一个栈帧：局部变量表、操作数栈、动态链接、方法出口 会（栈深度超限 StackOverflowError，扩展失败 OutOfMemoryError）
本地方法栈 私有 native 方法，HotSpot 里和虚拟机栈合并 同上
程序计数器 私有 当前线程执行的字节码行号 唯一不会 OOM 的区域
  • JDK 1.8 的关键变化：永久代（PermGen）被移除，换成元空间（Metaspace）。永久代在堆内、受 -XX:MaxPermSize 限制、字符串常量池在里面；元空间搬到本地内存、受本机总内存限制。
  • 为什么移除永久代：永久代大小难以预估（类加载多少不确定），小了 PermGen space OOM、大了浪费；换成元空间后按需扩展，同时把类元数据交给本地内存管理，简化 GC。

Q2：堆的分代结构？对象什么时候进老年代？
一句话结论：新生代占 1/3（Eden : S0 : S1 = 8 : 1 : 1），老年代占 2/3；对象在 Survivor 区每熬过一次 GC 年龄 +1，超过 15 岁晋升老年代。

  • 新生代（1/3）：Eden + Survivor0 + Survivor1，默认比例 8:1:1。Eden 满了触发 Minor GC，存活对象复制到 S0，清空 Eden 和 S1；下次 GC 时 Eden 和 S0 的存活对象复制到 S1，S0 清空（两块 Survivor 轮流当中转站，永远有一块是空的）。
  • 老年代（2/3）：长期存活的对象、大对象。
  • 晋升老年代的四种情况：
    1. 年龄到了阈值（默认 15，-XX:MaxTenuringThreshold 可调）。
    2. 大对象直接进老年代（避免在 Eden 和 Survivor 之间反复复制，-XX:PretenureSizeThreshold）。
    3. 动态年龄判断：Survivor 中相同年龄的对象总大小超过 Survivor 空间的一半，这个年龄及以上的直接晋升。
    4. 分配担保：Minor GC 前判断老年代剩余连续空间够不够放新生代所有对象（-XX:-HandlePromotionFailure），不够就直接 Full GC。
  • 为什么分代：绝大多数对象都是「朝生夕死」的，分代之后可以对不同区域用不同的回收算法——新生代用复制算法（存活少、复制成本低），老年代用标记-整理（存活多、不能用复制）。

Q3：怎么判断一个对象是垃圾？
一句话结论：引用计数法解决不了循环引用，Java 用的是可达性分析——从 GC Roots 出发，走不到的对象就是垃圾。

  • GC Roots 包括：
    • 虚拟机栈中栈帧的局部变量表引用的对象（最主力）
    • 方法区中类静态属性引用的对象
    • 方法区中常量引用的对象
    • 本地方法栈中 JNI 引用的对象
    • 活跃线程的引用、同步锁持有的对象等
  • 可达性分析的一个重要细节：不可达的对象不是马上死——要经历两次标记。第一次标记后判断是否要执行 finalize()，如果重写了并且还没执行过，会放进 F-Queue 里等一次 finalize()，如果这次自救成功（重新被引用上）就活下来。但生产代码不该依赖 finalize()。

Q4：GC 算法有哪些？
一句话结论：四种——标记-清除、复制、标记-整理、分代回收；新一代用复制，老年代用标记-整理。

算法 怎么做 优点 缺点 用在哪
标记-清除 标记存活对象，直接清除垃圾对象 实现简单、不需要移动对象 产生内存碎片；标记和清除都慢 CMS（老年代）
复制 内存分两块，把存活对象复制到另一块，整块清空原来的 没碎片、效率高 只能用一半内存 新生代（Serial/ParNew/Parallel Scavenge）
标记-整理 标记存活对象，然后全部向一端移动，清掉边界外的内存 没碎片 移动对象要更新引用，成本高 老年代（Serial Old/Parallel Old）
分代回收 按对象存活周期把堆分区，各区用最合适算法 综合效率最高 实现复杂 所有商用 JVM
  • 标记-清除的碎片为什么是问题：清理完之后内存是「活的-死的-活的-死的」交替，一个稍大的新对象可能找不到连续空间，只能提前触发下一次 GC。

Q5：常见的垃圾回收器？
一句话结论：新生代 Serial / ParNew / Parallel Scavenge；老年代 Serial Old / Parallel Old / CMS；G1 是整堆的；JDK 9 之后默认 G1。

回收器 区域 算法 特点
Serial / Serial Old 新生代/老年代 复制 / 标记-整理 单线程，GC 时全程 STW，客户端模式用
ParNew 新生代 复制 Serial 的多线程版，配合 CMS
Parallel Scavenge / Parallel Old 新生代/老年代 复制 / 标记-整理 多线程，吞吐量优先（适合后台批处理）
CMS 老年代 标记-清除 响应优先，停顿最短，但用标记-清除有碎片、并发阶段产生浮动垃圾
G1 整堆 复制 + 标记-整理 堆分成一块块 Region，可预测停顿（-XX:MaxGCPauseMillis），无碎片，适合大堆
  • Minor GC / Major GC / Full GC：
    • Minor GC（Young GC）：只回收新生代，Eden 满时触发，频率高、停顿短。
    • Major GC：主要回收老年代。
    • Full GC：回收整个堆 + 方法区，最慢、停顿最长，要尽量避免。
  • Full GC 的触发条件：System.gc()（建议但不保证，生产要禁掉）、老年代空间不足、分配担保失败、元空间不足。

Q6：String 对象存在哪？new String("abc") 创建了几个对象？
一句话结论：字符串常量存在字符串常量池（JDK 1.7 后移到堆里）；new String("abc") 最多创建 2 个对象——常量池里一个、堆里一个。

  • String s = "abc"：直接去常量池找，有就返回引用，没有就创建一个。
  • String s = new String("abc")：先在常量池里检查 “abc” 是否已存在（不存在就创建第 1 个），再在堆里 new 一个 String 对象（第 2 个），s 指向堆里那个。所以最多 2 个、最少 1 个。
  • 为什么 String 设计成不可变：① 可以安全地做常量池共享；② hashCode 可以缓存（非常适合当 HashMap 的 key）；③ 线程安全；④ 安全性（数据库连接串、类名、文件路径等如果是可变的会出大问题）。
  • 补充：拼接字符串在编译期能确定的话，编译器会直接优化成一个常量；只有在循环里拼接才需要用 StringBuilder（String 每次拼接都新建对象）。

Q7：类加载的过程？双亲委派模型是什么？
一句话结论：类加载分七步——加载、验证、准备、解析、初始化、使用、卸载；双亲委派是「收到加载请求先问父亲，父亲说没有才自己加载」。

  • 七个阶段：
    1. 加载：读字节码，生成 Class 对象。
    2. 验证：文件格式、元数据、字节码、符号引用检查。
    3. 准备：给静态变量分配内存并赋零值（static int a = 5 在这一步 a 是 0，不是 5）。
    4. 解析：把符号引用替换为直接引用。
    5. 初始化：执行 <clinit>，此时才真正给静态变量赋 5。父类的 <clinit> 先执行。
    6. 使用。
    7. 卸载：类的所有实例都被回收 + 加载它的 ClassLoader 被回收 + Class 对象无引用，三者齐备才卸载。
  • 三级类加载器：BootstrapClassLoader（C++ 实现，加载 rt.jar 等核心库）← ExtensionClassLoader（jre/lib/ext）← ApplicationClassLoader（ClassPath）← 自定义类加载器。
  • 双亲委派的流程：ApplicationClassLoader 收到请求 → 委派给 Extension → 委派给 Bootstrap → 顶层找不到才逐层往下自己尝试加载。
  • 双亲委派的作用：① 保证类的唯一性——不会出现同一个 java.lang.String 被加载出两个不同的 Class；② 安全——防止你自定义一个 java.lang.String 把核心类库覆盖掉。

1.2 主流框架

1.2.1 Spring IoC 与 DI

Q1：IoC 和 DI 是什么？
一句话结论：IoC（控制反转）是把「创建对象、管理对象生命周期」的权力从开发者手里交给 Spring 容器；DI（依赖注入）是实现 IoC 的手段，把对象需要的依赖由容器注入进去。

  • 对比理解：不用 Spring 时，你要 new OrderService(new OrderMapper())，谁创建、什么时候创建、创建几个都由你决定。用了 Spring，你只声明 @Autowired，容器负责找（或创建）一个 OrderMapper 塞进来。
  • 依赖倒置原则（DIP）：这是设计原则，说的是「高层模块和低层模块都应该依赖抽象，而不是依赖具体实现」。IoC 是设计模式，DI 是编码技巧，三者不是一回事。
  • 三种注入方式：
方式 写法 评价
构造器注入 构造函数参数 官方推荐。依赖不可变、能保证对象创建完成就是完整状态、方便单元测试；Spring 4.3 之后单构造器可以省略 @Autowired
Setter 注入 @Autowired 标在 setter 上 适合可选依赖、需要重新注入的场景
字段注入 @Autowired 标在字段上 最常用但不推荐——无法用 final、不能脱离容器单测、循环依赖时更难发现

Q2：Bean 的生命周期？
一句话结论：注册 BeanDefinition → 实例化 → 属性填充 → Aware 回调 → BeanPostProcessor 前置 → init 方法 → BeanPostProcessor 后置 → 使用 → 销毁。

按这个顺序背，一步都别跳：

  1. **扫描并注册 BeanDefinition**：容器的「图纸」，描述这个 Bean 的类名、作用域、是否懒加载等。
  2. 实例化：反射调用构造器创建对象（此时属性都还是 null）。
  3. 属性填充：@Autowired 注入依赖（populateBean）。
  4. Aware 回调：按顺序 BeanNameAware → BeanFactoryAware → ApplicationContextAware，让 Bean 感知到自己叫什么、在哪个容器里。
  5. **BeanPostProcessor.postProcessBeforeInitialization()**：初始化前置处理。
  6. 初始化：@PostConstruct → InitializingBean.afterPropertiesSet() → 自定义 init-method。
  7. BeanPostProcessor.postProcessAfterInitialization()：初始化后置处理。AOP 代理就是在这生成的——AbstractAutoProxyCreator 在这一步判断要不要给这个 Bean 生成代理对象。
  8. 使用。
  9. 销毁：容器关闭时 @PreDestroy → DisposableBean.destroy() → 自定义 destroy-method。
  • 两个补充点：
    • AOP 代理是在初始化之后才有的，所以构造器里拿不到代理对象、也不能调被增强的方法。
    • prototype 作用域的 Bean，容器只管到创建完，销毁不管——调用方自己负责释放。

Q3：Bean 的作用域有哪些？Spring MVC 的 Controller 是单例还是多例？
一句话结论：Bean 默认是单例；Controller 也是单例，靠「无状态」来支撑并发。

  • 六种作用域：
作用域 说明
singleton（默认） 整个容器只有一个实例
prototype 每次 getBean 都新建一个；销毁不管
request 每个 HTTP 请求一个（**必须显式 @Scope("request")**）
session 每个 HTTP Session 一个
application 每个 ServletContext 一个
websocket 每个 WebSocket 会话一个
  • Controller 是单例：@Controller、@RestController 默认都是 singleton，整个容器一个实例。它看起来像「每次都是新的」，是因为它无状态——每个请求的数据都放在方法参数和局部变量里，不往成员变量里放，所以一个实例并发处理上万请求也不冲突。
  • request / session 这些作用域必须显式声明才有，不会默认生效。
  • 单例下真正要小心的是：如果 Controller 里放了会被改写的成员变量（比如 private int count），就有线程安全问题。正确解法不是改成 prototype，而是不要在 Controller 里放可变状态；真要存状态，用方法局部变量、ThreadLocal；非要用实例状态才声明 @Scope("prototype")，代价是每次请求都新建一个对象。
  • 一句话答法：「默认是单例的，所以我在 Controller 里不放可变的成员变量，要 request 作用域得显式加 @Scope。」

Q4：Spring 怎么解决循环依赖？为什么要三级缓存？
一句话结论：靠三级缓存提前暴露「早期引用」；必须三级不能两级，是为了保证有 AOP 时同一个 Bean 只有一个实例（代理对象）。

  • 三个缓存：
级别 名字 存什么
一级 singletonObjects 完全初始化好的单例 Bean（成品）
二级 earlySingletonObjects 已实例化但还没填充属性的早期引用（半成品），或早期代理
三级 singletonFactories ObjectFactory 工厂，getObject() 时按需产出原始对象或提前生成的代理
  • 流程（A 依赖 B，B 依赖 A）：
    1. 创建 A → 实例化 A，把 A 的工厂放进三级缓存。
    2. 填充 A 的属性，发现要 B → 去创建 B。
    3. 创建 B → 实例化 B，把 B 的工厂放进三级缓存。
    4. 填充 B 的属性，发现要 A → 从三级缓存拿到 A 的工厂，调用 getObject() 得到 A 的早期引用，放进二级缓存，删掉三级缓存的工厂 → B 注入成功，B 变成成品放进一级缓存。
    5. A 拿到 B，注入成功，A 变成成品放进一级缓存。
  • 为什么必须三级、二级不行：关键在AOP。假设只有二级缓存，那么在步骤 2 里 B 拿到的会是 A 的原始对象；但 A 初始化完如果有 AOP 增强，容器里最终放的是 A 的代理对象。这两个是不同的对象 —— 同一个 Bean 在容器里出现了两个实例，单例被破坏（最典型的就是 @Transactional 失效）。三级缓存存的是工厂而不是对象，把「要不要提前生成代理」这个决定延迟到真正被依赖的那一刻，保证全局只有一个。
  • 哪些情况解决不了：
    • 构造器注入的循环依赖——实例化都还没完成，没机会提前暴露。
    • prototype 作用域的循环依赖——不缓存，直接抛异常。
    • @Async 导致的循环依赖（代理创建时机更早）——实践中也常出问题。
  • 补充：Spring Boot 2.6+ 默认禁止循环依赖（spring.main.allow-circular-references=false），说明官方态度是「循环依赖本身就是设计问题，应该重构而不是靠三级缓存兜住」。

Q5：Spring 用到了哪些设计模式？
一句话记法：工厂（BeanFactory）、单例（Bean 默认单例）、代理（AOP）、模板方法（各种 *Template）、观察者（事件机制）、适配器（HandlerAdapter）、装饰器（BeanWrapper）。

1.2.2 Spring AOP

Q1：什么是 AOP？
一句话结论：面向切面编程——把散布在业务代码各处的「横切关注点」（日志、事务、权限、监控）抽出来，统一在切面里处理，业务代码只关心业务。

  • 要解决什么问题：没有 AOP 时，每个 Service 方法都要写一遍「开启事务 → 业务 → 提交」，代码重复且和业务混在一起。有 AOP 之后，业务代码干干净净，事务逻辑集中在 @Transactional 背后。
  • 核心概念：
    • 切面（Aspect）：横切逻辑的模块，就是一个标了 @Aspect 的类。
    • 连接点（JoinPoint）：程序执行过程中的一个点，Spring 里就是「方法执行」。
    • 切点（Pointcut）：一个表达式，选出哪些连接点要增强。
    • 通知（Advice）：增强的具体动作（做什么、什么时候做）。
    • 织入（Weaving）：把切面应用到目标对象、生成代理对象的过程。
  • 实现原理：动态代理。目标类实现了接口就用 JDK 动态代理（基于 InvocationHandler，生成实现同一接口的代理类）；没实现接口就用 CGLIB（通过继承生成子类，覆盖方法）。Spring Boot 2.x 起 spring.aop.proxy-target-class 默认是 true，也就是默认强制用 CGLIB，因为 CGLIB 能代理没有接口的类，更省心。

Q2：AOP 的通知类型有哪五种？
一句话结论：@Before 前置、@AfterReturning 返回、@AfterThrowing 异常、@After 最终、@Around 环绕——环绕最强。

注解 名称 执行时机 能拿到什么
@Before 前置通知 目标方法执行前 方法参数，拿不到返回值
@AfterReturning 返回通知 目标方法正常返回后 用 returning 属性拿返回值
@AfterThrowing 异常通知 目标方法抛异常后 用 throwing 属性拿异常对象
@After 最终通知 无论正常还是异常都执行 等价于 finally
@Around 环绕通知 把目标方法整个包起来 ProceedingJoinPoint，功能最强

Q3：环绕通知为什么最强？它有哪些常用方法？
一句话结论：因为它能决定目标方法执不执行、能改参数、能改返回值、能捕异常——另外四种通知都做不到。

  • 它多出来的能力：
    1. 能决定目标方法要不要执行——不调 proceed() 就等于把方法拦掉了（可以做权限校验、幂等拦截）。
    2. 能改参数——getArgs() 拿出来改了，再 proceed(newArgs) 传进去。
    3. 能改返回值——proceed() 的返回值可以直接替换掉。
    4. 能捕异常——try-catch 包住 proceed()，可以吞掉异常或者抛别的异常。
    5. 能重复执行——可以 proceed() 调多次（实现重试）。
  • ProceedingJoinPoint 最常用的三个方法：
    1. proceed() —— 执行目标方法，可以传新的参数进去，返回值就是目标方法的返回值。
    2. getArgs() —— 拿到目标方法的参数数组，可以读也可以改。
    3. getSignature() —— 拿到方法签名（方法名、所属类、参数类型），日志和埋点里最常用。
  • 另外还有两个：getTarget() 拿目标对象、getThis() 拿当前代理对象。
  • ⚠️ **返回值类型必须写成 Object**——因为返回值可以被替换，写死成具体类型会编译不过。

Q4：@Transactional 和 AOP 是什么关系？
一句话结论：@Transactional 底层就是一个环绕通知——TransactionInterceptor 在目标方法前后开启和提交事务。

  • TransactionInterceptor 实现了 MethodInterceptor，本质就是环绕增强：
    • 方法执行前：根据传播行为决定是加入现有事务还是新开一个事务。
    • 方法正常返回：提交事务。
    • 方法抛异常：根据 rollbackFor 判断要不要回滚。
  • 把 AOP 和事务串起来讲，比单独答 AOP 加分——它说明你理解的是机制而不是注解。
  • 这也是「同类内部方法调用事务失效」的根因：this.methodB() 走的是原始对象，不经过代理，所以切面根本没机会执行。

Q5：项目里 AOP 用在哪个地方？
一句话记法：公共字段自动填充（创建时间 / 更新时间）。

  • 痛点：每个 insert 都要写 setCreateTime(LocalDateTime.now())，每个 update 都要写 setUpdateTime(...)，重复且容易忘。
  • 做法：
    1. 自定义注解 @AutoFill(OperationType.INSERT)，标在 Mapper 方法上，用枚举区分是插入还是更新。
    2. 写一个 @Aspect 切面，切点是 @annotation(com.example.annotation.AutoFill)。
    3. 在环绕通知里用 pjp.getArgs() 拿到方法参数，判断参数是不是实体对象、是不是实现了统一的 BaseEntity 接口（里面定义了 createTime / updateTime / createUser / updateUser 字段）。
    4. 用反射调 setCreateTime(LocalDateTime.now())，然后 pjp.proceed(args) 把改过的参数传进去。
  • 顺带的收获：这个场景同时也用到了反射（动态调 setter）和注解（标记哪些方法需要填充），是「AOP + 注解 + 反射」三件套的经典组合，面试时可以从任一个角度切进去讲。

1.2.3 声明式事务

Q1：@Transactional 的传播行为有哪些？
一句话结论：七种，最常用的是 REQUIRED（默认）和 REQUIRES_NEW。

传播行为 含义
REQUIRED（默认） 有事务就加入，没有就新建。最常用
REQUIRES_NEW 无论有没有，都新建一个独立事务，外层事务挂起。适合「日志记录必须成功，不受业务回滚影响」
NESTED 嵌套事务，用 savepoint 实现，内层回滚不影响外层（但外层回滚内层也会回滚）
SUPPORTS 有就用，没有就非事务执行
NOT_SUPPORTED 以非事务方式执行，有事务就挂起
MANDATORY 必须在事务中，否则抛异常
NEVER 必须不在事务中，否则抛异常
  • REQUIRED vs REQUIRES_NEW 的区别：前者内外是一个事务，外层回滚内层跟着回滚；后者是两个独立事务，外层回滚不影响已提交的内层。经典场景是「下单失败要回滚，但失败日志要留下」，日志方法就得用 REQUIRES_NEW。

Q2：@Transactional 什么情况下会失效？
一句话结论：六种——同类内部调用、方法不是 public、异常被吞掉、异常类型不对（默认只回滚 RuntimeException）、多数据源没配对、传播行为配错。

失效场景 原因 怎么修
同类内部方法调用（this.methodB()） 走的是原始对象，不经过代理，切面没机会执行 注入自己（@Autowired 自己）、AopContext.currentProxy()、或者把方法拆到另一个 Bean
方法不是 public Spring AOP 代理只能拦截 public 方法 改成 public
异常被 catch 吞了 代理感知不到异常，认为方法正常返回就提交了 别吞；或者 catch 里手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()
抛的是受检异常 默认只对 RuntimeException 和 Error 回滚 @Transactional(rollbackFor = Exception.class)
多数据源没指定事务管理器 不知道用哪个 PlatformTransactionManager @Transactional(transactionManager = "xxxManager")
传播行为配错 比如配了 NOT_SUPPORTED，本身就是「不要事务」 改成 REQUIRED
  • 第一条是最常问的，要能讲透：Spring 事务靠 AOP 代理实现，this.methodB() 这个 this 是原始对象不是代理对象，所以根本不进切面。解法是把 methodB 挪到另一个 Bean 里，或者用 AopContext.currentProxy() 拿到代理再调。

Q3：MySQL 的隔离级别和 @Transactional 的隔离级别是一回事吗？
一句话结论：不是。@Transactional(isolation = ...) 配的是「Spring 告诉数据库要用哪个隔离级别」，最终由数据库执行；配了不生效往往是数据库或连接池不支持。

  • @Transactional(isolation = Isolation.REPEATABLE_READ) 最终会翻译成一条 SET TRANSACTION ISOLATION LEVEL REPEATABLE READ 发给数据库连接。
  • 所以它受数据库限制——如果数据库本身（比如某些分布式数据库）不支持某个隔离级别，配了也没用。
  • 实际项目里很少改这个，因为默认用数据库的默认隔离级别（MySQL 就是可重复读）就够用了。

1.2.4 Spring MVC

Q1：Spring MVC 的请求处理流程？
一句话结论：DispatcherServlet 是前端控制器，它问 HandlerMapping「这个 URL 谁处理」，再让 HandlerAdapter 去调，拿到 ModelAndView 后交给 ViewResolver 解析成 View 渲染。

按顺序说：

  1. 请求到达 **DispatcherServlet**（前端控制器，所有请求的总入口）。
  2. DispatcherServlet 问 HandlerMapping：这个 URL 映射到哪个 Handler？HandlerMapping 返回一个 HandlerExecutionChain（Handler + 拦截器链）。
  3. DispatcherServlet 把 Handler 交给 **HandlerAdapter**，由它去调用具体的方法（适配器的意义在于：Handler 可以是注解方法、可以是实现 Controller 接口的类、也可以是 HttpRequestHandler，适配器把它们统一起来）。
  4. Handler 执行完返回 **ModelAndView**。
  5. DispatcherServlet 把 ModelAndView 交给 **ViewResolver**，解析出真正的 View。
  6. View 渲染（把 model 数据填进去，生成 HTML/JSON）。
  7. 响应返回给客户端。
  • 拦截器的三个方法在流程中分别对应：preHandle（步骤 3 之前）、postHandle（步骤 4 之后、渲染之前）、afterCompletion（渲染完成后）。

Q2：拦截器和过滤器有什么区别？
一句话结论：过滤器是 Servlet 规范的（更靠外、能拿到原始请求、不能直接注入 Spring Bean），拦截器是 Spring MVC 的（更靠内、能拿到 Handler 信息、可以注入 Bean）。

维度 Filter（过滤器） Interceptor（拦截器）
规范 Servlet 规范（javax.servlet.Filter） Spring MVC 自己的
作用范围 所有请求，包括静态资源 只拦截 Controller 请求
执行时机 Servlet 之前 DispatcherServlet 之后、Controller 之前
能否注入 Bean 默认不能（可以靠 DelegatingFilterProxy 解决） 可以，本身就是 Spring 管理的
方法 doFilter 一个方法 preHandle / postHandle / afterCompletion 三个
能拿到什么 原始 ServletRequest HandlerMethod，能知道要执行哪个方法、有什么注解
  • 项目里的用法：用拦截器（UserContextInterceptor）读 X-User-Id 请求头存进 ThreadLocal。用拦截器不用过滤器的原因就是它能注入 Spring Bean，也能更精确地排除白名单路径（用 addPathPatterns("/**").excludePathPatterns(...)）。

1.2.5 Spring Boot

Q1：Spring 和 Spring Boot 的区别？
一句话结论：Spring 是一个生态（提供了 IoC、AOP、MVC、事务等能力），Spring Boot 是「快速开发脚手架」——核心理念是约定大于配置，用 starter 把依赖打包，用自动装配把配置干掉。

  • Spring 的痛点：以前搭一个 Web 项目要写一堆 XML（数据源、事务管理器、MVC 配置、视图解析器……），版本还要自己对齐，换个项目就重来一遍。
  • Spring Boot 解决了什么：
    1. starter 依赖打包：spring-boot-starter-web 一个依赖把 Web 开发要用的东西全带进来，版本已经对齐过了。
    2. 自动装配：@EnableAutoConfiguration 自动把需要的 Bean 配好，不用手写 XML。
    3. 约定大于配置：默认端口 8080、默认配置文件 application.yml、默认静态资源目录 static/，你不动它就能跑。
    4. 内嵌容器：内嵌 Tomcat，打成 jar 直接 java -jar 就能跑，不用装 Tomcat 部署 war。

Q2：Spring Boot 自动装配的原理？
一句话结论：@SpringBootApplication 里的 @EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 去读所有 jar 包里的 META-INF/spring.factories（Spring Boot 2.7+ 是 META-INF/spring/*.imports），拿到候选配置类，再用 @ConditionalOnXxx 过滤，最后导入容器。

链路展开：

  • @Conditional 是关键：它保证了「你引了 spring-boot-starter-web，才装配 Tomcat 和 MVC 的东西；没引，就不装配」。这就是为什么「导入就能用」——按需装配。
  • 常见条件注解：@ConditionalOnClass（类路径有某个类才生效）、@ConditionalOnMissingBean（容器里没有这个 Bean 才生效，这是你自定义配置能覆盖默认配置的原因）、@ConditionalOnProperty（配了某个属性才生效）。
  • 自定义 starter 就是反过来做：建一个 Maven 模块 → 写 @Configuration + @ConfigurationProperties → 在 META-INF 里注册这个配置类 → 别人引你的依赖就自动生效。

Q2：MyBatis 的优缺点？
一句话结论：优点是 SQL 完全可控、灵活、好优化；缺点是 SQL 写在 XML 里，和 Java 代码分离，改起来要两边对；复杂 SQL 维护成本高。

  • 相比 JPA/Hibernate：JPA 全自动生成 SQL，开发快但SQL 不可控，出了慢查询不好优化；MyBatis 是「半自动」，SQL 自己写，性能可控，适合互联网业务。
  • MyBatis 的核心组件：SqlSessionFactoryBuilder（读配置建工厂）→ SqlSessionFactory（工厂）→ SqlSession（一次会话）→ Executor（执行器，真正干活）→ MappedStatement（一条 SQL 的完整描述）。

Q3：MyBatis-Plus 比 MyBatis 多了什么？
一句话记法：BaseMapper 内置 CRUD、条件构造器、代码生成器、分页插件、逻辑删除。

能力 说明

Q4：MyBatis 的动态 SQL 标签用过哪些？

  • <if>：条件判断，比如「传了 name 才拼 AND name = #{name}」。

  • <set>：用在 UPDATE 里，自动加 SET 并去掉末尾多余的逗号。
  • <choose> / <when> / <otherwise>：相当于 Java 的 switch-case。
  • <trim>：<where> 和 <set> 的通用版，可以自定义前缀后缀和要去掉的字符。

1.2.7 Spring Cloud Alibaba

Q1：Spring Boot 和 Spring Cloud 是什么关系？
一句话结论：Spring Boot 是用来构建单个应用的，Spring Cloud 是用来构建分布式系统的——它基于 Spring Boot，把「服务注册发现、配置中心、负载均衡、断路器、网关」这些分布式问题各自封装成一个组件。

  • Spring Boot 解决「单体应用怎么快速开发」；Spring Cloud 解决「拆成多个服务之后，服务之间怎么找到彼此、怎么调用、怎么保护、怎么统一配置」。
  • 一句话：Spring Cloud 是分布式系统的整体解决方案，Spring Boot 是它的实现载体。

Q2：Spring Cloud Alibaba 有哪些组件？各自解决什么问题？
一句话记法：Nacos 解决「服务怎么找到彼此 + 配置怎么统一管」，Gateway 解决「统一入口与鉴权」，OpenFeign 解决「服务怎么调用」，Seata 解决「跨库怎么保证一致」，Sentinel 解决「流量太大/下游挂了怎么办」。

Q3：Nacos 和 Eureka 的区别？
一句话结论：Eureka 只有注册中心，Nacos 既是注册中心又是配置中心，还支持 AP/CP 切换和配置热刷新。

  • 功能范围：Eureka 只有服务注册发现；Nacos 还带配置中心（可以动态改配置、热刷新，不用重启）。
  • 一致性模型：Eureka 只有 AP（保证可用性，可能读到旧数据）；Nacos 支持 AP 和 CP 模式切换（临时实例用 AP，持久化实例用 CP）。
  • 健康检查：Eureka 靠客户端心跳；Nacos 支持心跳和主动探测两种。
  • 界面：Nacos 有管理控制台，能直接看服务列表、改配置、看实例数。

Q4：Nacos 同时当注册中心和配置中心，配置是怎么加载的？为什么需要 bootstrap.yml？
一句话结论：bootstrap.yml 在 Spring 生命周期里最先加载，用它拿到 Nacos 地址再去读配置中心的配置；这是为了解决「连 Nacos 需要配置，但配置又在 Nacos 里」的鸡生蛋问题。

  • 加载顺序（优先级从低到高）：
    1. **bootstrap.yml**（最先加载）：只放最小必要信息——服务名、Nacos 地址、profile、要拉哪些 shared-configs。
    2. Nacos 配置中心：shared-configs（公共配置：数据库、Redis、JWT、MyBatis）+ extension-configs（服务私有配置）。
    3. application.yml（本地私有，优先级最高，可以覆盖远程）。
  • 优先级口诀：本地 > 远程，服务私有 > 共享。
  • 配置分层原则：判断标准就一句话——「多个服务用不用？」 多个服务都用（数据库连接、Redis、JWT 密钥）放 shared-configs；只有自己用（自己的端口、自己的库名）放服务私有的 extension。

Q5：Nacos 配置怎么做到热刷新的？
一句话结论：@RefreshScope 标记的 Bean 会被放进一个特殊的 Scope，配置变更时 Spring 发 EnvironmentChangeEvent，把这个 Scope 里的 Bean 标记为「已失效」，下次访问时用新配置重新创建。

流程：

  1. 在 Nacos 控制台改配置并发布。
  2. Nacos 推送变更到客户端（长轮询机制，客户端发起请求后服务端 hold 住 30 秒，有变化立刻返回）。
  3. Spring Cloud 收到后刷新 Environment，发布 EnvironmentChangeEvent 事件。
  4. RefreshScope 收到事件，销毁被标注的 Bean 缓存。
  5. 下次 getBean 时用新的配置值重建这个 Bean。

用法：@Component + @RefreshScope + @ConfigurationProperties(prefix = "sky.jwt")。

  • ⚠️ 一个必须知道的坑：不加 @RefreshScope 的 Bean 不会刷新。如果用 @Value 直接注入，改了 Nacos 配置不会生效——因为 @Value 在 Bean 创建时就写死了。
  • 另一个坑：**数据库连接池、线程池这类 Bean 千万不要加 @RefreshScope**——刷新会导致连接池重建，线上会出现连接抖动。

Q6：Gateway 和 Nginx 有什么区别？为什么不直接用 Nginx 做鉴权？
一句话结论：Nginx 是基础设施层的反向代理/负载均衡（面向运维，管静态资源和流量的分发），Gateway 是业务层的统一入口（面向开发，管鉴权、路由、限流）。

擅长 静态资源托管、反向代理、负载均衡、HTTPS 卸载 JWT 验签、按用户身份鉴权、动态路由、限流、跨域
动态性 改配置要 reload 路由规则可以放 Nacos，改了立即生效
能不能做鉴权 技术上能（ngx_lua），但要把业务逻辑写进 Nginx，维护成本高、团队不够熟悉 就是为此设计的，Java 写的，跟前端团队同一套技术栈

Q7：为什么选 Gateway 不选 Zuul？
一句话结论：Gateway 基于 Spring WebFlux（响应式、非阻塞、异步），性能比基于 Servlet 的 Zuul 1.x 好，而且是 Spring 官方主推的。

  • Zuul 1.x 是阻塞式的，一个请求占一个线程，高并发下线程池容易被打满；Gateway 基于 Reactor + Netty，用少量的线程处理大量请求。
  • Zuul 2.x 虽然也改成异步了，但 Spring Cloud 社区没有整合，所以事实上被 Gateway 取代了。
  • ⚠️ 用 Gateway 有个必须知道的坑：它跑在 WebFlux（响应式）环境里，不兼容 Servlet 体系。所以你的 HandlerInterceptor、HttpServletRequest 这些在网关里全用不了，启动会直接报 HandlerInterceptor.class not found。解法是把 Servlet 相关的依赖（spring-boot-starter-web）从网关模块排掉，同时 @ComponentScan 排除掉带拦截器的包。

Q8：OpenFeign 和 RestTemplate 的区别？
一句话结论：RestTemplate 是「手动调 HTTP」，要自己拼 URL、自己解析响应；OpenFeign 是「声明式调用」——写一个接口加注解，用起来像调本地方法，底层自动帮你发 HTTP 请求。

1.3.1 MySQL 索引

Q1：为什么用 B+ 树做索引？B+ 树和 B 树的区别？
一句话结论：B+ 树只有叶子节点存数据、非叶子节点只存索引键，所以同样大小的节点能放更多键，树更矮、IO 次数更少；而且叶子节点之间有链表，范围查询和排序特别方便。

  • 和 B 树的区别：
B 树 B+ 树
数据存放 每个节点都存数据 只有叶子节点存数据，非叶子节点只存键
一个节点能放的键 少（因为要腾地方放数据） 多（只存键）
树的高度 高 矮（3~4 层就能存千万级数据）
范围查询 要中序遍历，来回跳 叶子节点有双向链表，顺序扫就行
查询稳定性 不稳定（有时在非叶节点命中，有时到叶子） 稳定（任何查询都要走到叶子）
  • 为什么不选红黑树/二叉树：二叉树在数据量大时高度太高。一千万数据，二叉树要找 20 多次（每次一个磁盘 IO），B+ 树三层就够了（3 次 IO）。磁盘 IO 次数就是数据库性能的关键。
  • 为什么不选哈希索引：哈希索引 O(1) 很快，但只支持等值查询，不支持范围查询和排序，而业务里 BETWEEN、>、ORDER BY 到处都是。

Q2：聚簇索引和非聚簇索引的区别？什么是回表？
一句话结论：聚簇索引（主键索引）的叶子节点直接存整行数据；二级索引的叶子节点存的是主键值。用二级索引查到主键后，还要再回主键索引查一次整行——这就是回表。

  • 聚簇索引：InnoDB 的主键索引就是聚簇索引，叶子节点直接是数据行。一张表只能有一个聚簇索引。
  • 主键怎么选：① 有主键就用主键；② 没有主键就用第一个不含 NULL 的唯一列；③ 都没有，InnoDB 自动生成一个隐藏的自增 rowid 当主键。
  • 二级索引（辅助索引）：叶子节点存的是「索引列的值 + 主键值」。所以按二级索引查完，拿到主键，还要再走一次聚簇索引才能拿到整行——这就是回表。
  • 为什么要回表：因为二级索引里只有索引列和主键，没有其他列的数据。
  • 怎么避免回表：用覆盖索引——查询要用的字段全部都在索引里，不用再回去查整行。

Q3：什么是覆盖索引？
一句话结论：一个查询需要的所有列都在索引里，不用回表，直接从索引就能拿到全部结果。

  • 怎么验证：EXPLAIN 的 Extra 列出现 Using index 就说明用上了覆盖索引。
  • 覆盖索引的价值：省掉一次回表，IO 减半。这就是为什么「不要写 SELECT *」——SELECT * 必然要回表，覆盖索引根本用不上。

Q4：联合索引的最左前缀原则？
一句话结论：联合索引 (a, b, c) 的 B+ 树是按 a 排序、a 相同按 b 排序、b 相同按 c 排序，所以查询必须从最左边的字段开始，才能用上索引。

  • 关键规则：遇到范围查询（>、<、BETWEEN、LIKE 'x%'），它后面的字段就停止匹配。
  • 为什么：B+ 树在 b > 2 这个范围内，c 并不是全局有序的（只在每个 b 值内部有序），所以没法用索引定位 c。
  • 联合索引字段顺序怎么定：把区分度高的放前面。区分度 = COUNT(DISTINCT 列) / COUNT(*)，越接近 1 越适合放前面。
  • 一个例外（区分度太低的情况）：如果一个字段区分度特别低（比如性别，只有男女），优化器可能直接忽略整个索引选择全表扫描——因为走索引再回表的成本比全表扫还高。**经验界线是 30%**：一个条件过滤掉的数据不到 30%，优化器倾向于走索引；超过就可能放弃。

Q5：索引失效的情况有哪些？
一句话结论：六种——模糊查询左模糊、索引列上用函数、索引列上做运算、字符串和数字比较、不遵守最左前缀、OR 连接了非索引列。

Q6：EXPLAIN 要看哪些字段？
一句话结论：重点看 type（访问类型，越高越好）、key（实际用了哪个索引）、rows（预估扫描行数）、Extra（有没有 filesort / temporary / 用没用覆盖索引）。

Q7：怎么优化一条慢 SQL？
一句话结论：先 EXPLAIN 找到慢在哪，再分四类下手——加/改索引、改写 SQL、减少数据量、加缓存。

  1. EXPLAIN 定位：看 type 是不是 ALL、key 是不是 NULL、Extra 有没有 filesort / temporary。
  2. 索引层面：建合适的索引（WHERE / ORDER BY / JOIN / GROUP BY 涉及的字段）；建联合索引时遵守最左前缀、把区分度高的放前面；能用覆盖索引就避免 SELECT *；考虑前缀索引（长字符串只索引前 N 个字符）。
  3. SQL 层面：不要在索引列上用函数/运算；避免左模糊；OR 改 UNION；小表驱动大表（IN 的子查询结果集小就用 IN，大就用 EXISTS）。
  4. 数据量层面：深分页优化——LIMIT 1000000, 10 会扫 100 万行，改成 WHERE id > 1000000 LIMIT 10（前提是 id 自增且连续）；大表历史数据归档。
  5. 架构层面：热点数据加 Redis 缓存；读写分离（主库写、从库读）；单表数据量超千万考虑分库分表。
  • 深分页为什么慢：LIMIT offset, size 不是「跳过 offset 行」这么轻松——MySQL 必须先查出 offset + size 行，再把前 offset 行丢掉，所以 offset 越大扫得越多。用「记住上一页最后一条 id」的游标方式，就能直接定位，一步到位。

Q8：索引是不是建得越多越好？
一句话结论：不是。索引占空间，而且每次增删改都要维护所有索引，写性能会下降。

  • 索引的代价：
    1. 占磁盘空间（索引本身也是数据）。
    2. 拖慢写入——每次 INSERT / UPDATE / DELETE 都要同步更新所有相关索引的 B+ 树，还可能触发页分裂。
    3. 优化器选择成本变高——候选索引太多，选错的概率也会上升。
  • 适合建索引：WHERE / ORDER BY / GROUP BY / JOIN ON 里高频出现的字段；区分度高的字段（唯一性字段）；需要保证唯一性的字段（唯一索引）。
  • 不适合建索引：区分度极低的字段（性别、状态只有 0/1 且分布均匀）；很少作为查询条件；表数据量本来就很小（全表扫更快）；频繁更新的字段（比如用户余额——每次改都要维护索引）。

1.3.2 MySQL 事务

Q1：事务的 ACID 是怎么实现的？
一句话结论：原子性靠 undo log，持久性靠 redo log，隔离性靠 MVCC + 锁，一致性是前三者共同保证的结果。

特性 含义 靠什么实现
A 原子性 事务里的操作要么全成功要么全失败 undo log（回滚日志）——记录了「怎么撤销」，回滚时反向执行
C 一致性 事务前后数据都满足业务约束 前三者共同保证的结果，不是某个机制
I 隔离性 并发事务之间互不干扰 MVCC（快照读）+ 锁（当前读）
D 持久性 提交后的数据不会丢 redo log（重做日志）+ WAL

Q2：并发事务会带来哪些问题？
一句话结论：三个——脏读（读到别人没提交的）、不可重复读（同一行两次读值不一样）、幻读（两次范围查多出来几行）。

问题 一句话定义 本质
脏读 读到了别人还没提交的数据，别人一回滚，我读到的就是假的 读了未提交的数据
不可重复读 同一个事务里两次读同一行，结果不一样（因为别人在中间 update 并提交了） 这一行的值变了
幻读 同一个事务里两次范围查询，第二次多出来几行（因为别人在中间 insert 并提交了） 多了几行

不可重复读和幻读最容易混，一句话区分：不可重复读管的是「这一行的值变了」，幻读管的是「多了几行」。

Q3：四个隔离级别？MySQL 默认是哪个？
一句话结论：读未提交、读已提交、可重复读（MySQL 默认）、串行化；级别越高一致性越强，并发性能越差。

隔离级别 脏读 不可重复读 幻读
读未提交（Read Uncommitted） 会 会 会
读已提交（Read Committed, RC） 不会 会 会
可重复读（Repeatable Read, RR）← MySQL InnoDB 默认 不会 不会 InnoDB 下基本不会
串行化（Serializable） 不会 不会 不会
  • 两个必须主动说的点：
    • MySQL InnoDB 默认是可重复读，这是它的特点——Oracle 和 PostgreSQL 默认都是读已提交。
    • 可重复读下幻读是怎么解决的：普通查询（快照读）走 MVCC，读的是事务开始时的快照，看不到新插入的行；加锁查询（当前读，比如 SELECT ... FOR UPDATE）走 next-key lock（临键锁），把记录本身和它前面的间隙一起锁住，不让别人在间隙里插入。

Q4：MVCC 的原理？
一句话结论：每行记录有隐藏的 trx_id（最后修改它的事务 ID）和 roll_pointer（指向 undo log 旧版本），这些版本串成「版本链」；读的时候根据 Read View 判断哪个版本对我可见。

  • 两个隐藏列（InnoDB 聚簇索引每行都有）：
    • **trx_id**：最后一次修改这行的事务 ID。
    • roll_pointer：指向 undo log 里这个行上一个版本的指针，顺着它能一直找到最早的历史版本，形成版本链。
  • Read View 的四个字段：
字段 含义
m_ids 生成 Read View 时，还没提交的事务 ID 列表
min_trx_id m_ids 里的最小值
max_trx_id 下一个要分配的事务 ID（注意不是 m_ids 的最大值，而是全局最大 ID + 1）
creator_trx_id 创建这个 Read View 的事务自己的 ID
  • 可见性判断规则（拿到一个版本的 trx_id 后）：
    1. trx_id < min_trx_id → 这个版本在 Read View 创建前就提交了，可见。
    2. trx_id >= max_trx_id → 这个版本在 Read View 创建后才开始，不可见。
    3. min_trx_id <= trx_id < max_trx_id → 看 trx_id 在不在 m_ids 里：在 = 还没提交 = 不可见；不在 = 已提交 = 可见。
    4. 补充：自己改的数据永远可见。
  • RC 和 RR 的唯一区别就在 Read View 的生成时机：
    • 读已提交（RC）：每次 SELECT 都重新生成一个 Read View → 所以每次都能读到别人最新提交的数据 → 有不可重复读。
    • 可重复读（RR）：只在第一次 SELECT 时生成一个，之后全程复用 → 所以整个事务看到的是同一份快照 → 没有不可重复读。
  • 可重复读下为什么还可能有幻读：快照读看不到新插入的行，但如果你在事务里做了 UPDATE（当前读），它会读到最新数据并且把被更新记录的 trx_id 改成自己的事务 ID，之后你再 SELECT 就能看到这行了——看起来就像凭空多了一行。这就是 RR 下 MVCC 兜不住幻读的场景。补救办法是事务一开始就用 SELECT ... FOR UPDATE 加 next-key lock。

Q5：SELECT ... FOR UPDATE、UPDATE 这些「当前读」和普通 SELECT 有什么区别？
一句话结论：普通 SELECT 是快照读，读的是历史版本、不加锁；SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE / INSERT 是当前读，读的是最新版本、要加锁。

快照读 当前读
语句 普通 SELECT SELECT ... FOR UPDATE（X 锁）、SELECT ... LOCK IN SHARE MODE（S 锁）、UPDATE、DELETE、INSERT
读什么 MVCC 版本链里对自己可见的那个版本 最新已提交的版本
加锁 不加锁 加锁（行锁 / 临键锁）
目的 高并发读，不加锁所以快 保证读到的数据能立刻被安全地修改
  • 这个区分在项目里很实用：日常查询全部走快照读（走 MVCC，不加锁，性能好）；只有要「读出来再改」的场景（比如扣减）才用当前读加锁。

Q6：大事务有什么危害？
一句话结论：锁释放得晚、回滚段膨胀、执行时间长、主从延迟大。

  1. 锁持有时间长：UPDATE 加的锁要到事务提交后才释放，大事务锁住的行多、时间久，容易造成别的请求等待甚至锁超时、死锁。
  2. undo log 膨胀：回滚记录要一直保留到事务结束，长事务会让回滚段越来越大。
  3. 主从延迟：主库执行 10 分钟，从库就得回放 10 分钟，这段时间主从数据是不一致的，读到从库会读到旧数据。
  4. 长事务还会拖慢 purge：MVCC 的旧版本要靠 purge 线程清理，长事务会阻止它清理，导致 undo 空间持续膨胀。
  • 实践建议：事务里不要放远程调用（Feign、调第三方接口）、不要做大批量操作、不要循环里提交；能拆小就拆小。

1.3.3 MySQL 锁

Q1：MySQL 有哪些锁？
一句话结论：按粒度分三级——全局锁（FTWRL，全库只读）、表级锁（表锁、元数据锁 MDL、意向锁、AUTO-INC 锁）、行级锁（InnoDB 独有）。

  • 全局锁：FLUSH TABLES WITH READ LOCK，整个库变成只读，用于全库逻辑备份。
  • 表级锁：
    • 表锁：LOCK TABLES ... READ/WRITE，开销小但并发差。
    • 元数据锁（MDL）：不需要显式加，MySQL 自动加的。增删改查时加读锁，改表结构时加写锁。读锁之间不互斥，读锁和写锁互斥。经典的坑：一个长事务持有 MDL 读锁，这时候你想加个字段（要写锁）就会一直等，后面所有请求也跟着排队。
    • 意向锁：快速判断「表里有没有行被锁住」，避免加表锁时逐行检查。
  • 行级锁（InnoDB 独有），三种：
    • 记录锁（Record Lock）：锁住一行记录本身。
    • 间隙锁（Gap Lock）：锁住两条记录之间的间隙，防止别人在这个间隙里插入。只在可重复读级别有。
    • 临键锁（Next-Key Lock）：记录锁 + 间隙锁，锁住「记录本身 + 它前面的间隙」。RR 下加锁的默认单位，就是它解决了幻读。

Q2：两个事务 UPDATE 同一行会阻塞吗？UPDATE 不同的主键范围呢？
一句话结论：同一行一定阻塞（X 锁互斥）；不同范围不阻塞（每个范围锁在自己的间隙里，不重叠）；但如果 WHERE 用的不是索引列，就会锁全表。

  • 同一行：UPDATE 加的是 X 记录锁，X 和 X 互斥，必然阻塞。
  • 不同范围：WHERE id < 10 锁的是 (-∞, 10) 这个区间，WHERE id > 15 锁的是 (15, +∞)，两个区间不重叠，所以不阻塞。
  • ⚠️ 最需要注意的一种: UPDATE t SET ... WHERE name = 'x'，如果 name 上没有索引，InnoDB 没法用索引定位行，只能全表扫描。而全表扫描会给扫到的每一行都加锁，还会给所有间隙加间隙锁——4 条记录就是 4 个记录锁 + 5 个间隙锁，相当于锁了整张表，所有更新都得排队。
  • 所以一条重要实践是：UPDATE / DELETE 的 WHERE 条件一定要走索引。

Q3：什么是死锁？怎么避免？
一句话结论：四个必要条件——互斥、持有并等待、不可剥夺、循环等待；破坏任意一个就能避免，工程上最常用的是「按固定顺序访问资源」破坏循环等待。

  • 在数据库里的表现：事务 A 锁了行 1 要锁行 2，事务 B 锁了行 2 要锁行 1，互相等，死锁。
  • MySQL 的处理：InnoDB 有死锁检测（innodb_deadlock_detect），检测到死锁会主动回滚代价小的那个事务，让另一个继续。所以通常表现为「其中一个事务报 Deadlock found 错误」而不是永久卡死。
  • 避免手段：
    1. 按固定顺序访问（最有效）：比如批量更新时，先把 id 排序再更新，这样所有事务加锁顺序一致，不会有环。
    2. 缩短事务：事务越小、持锁时间越短，撞上的概率越低。
    3. 一次性锁住需要的资源：别一个一个来。
    4. WHERE 走索引：避免扩大锁范围。

1.3.4 MySQL 日志

Q1：MySQL 有哪几种日志？
一句话结论：redo log（InnoDB 层，保持久性）、undo log（InnoDB 层，保原子性 + 支撑 MVCC）、binlog（Server 层，做主从复制和数据恢复）、relay log（从库的中继日志）、慢查询日志。

日志 层级 作用
redo log InnoDB 引擎层 崩溃恢复、保证持久性；物理日志，记录「某个数据页做了什么修改」
undo log InnoDB 引擎层 回滚、保证原子性；同时是 MVCC 版本链的来源；逻辑日志，记录「反向操作」
binlog Server 层 主从复制、数据备份恢复；逻辑日志，记录所有写操作（不记录 SELECT）
relay log 从库 从库收到的 binlog 暂存，等待回放
慢查询日志 Server 层 记录执行超时的 SQL，用于调优

Q2：为什么有了 undo log 还需要 redo log？
一句话结论：两者作用相反——undo 记录「事务开始前的值」用于回滚，redo 记录「事务完成后的值」用于崩溃恢复；提交前崩溃用 undo 回滚，提交后崩溃用 redo 恢复。

undo log redo log
记录什么 事务开始前的旧值（更新记旧值、插入记主键、删除记全部内容） 事务完成后的新值（物理修改）
干什么用 回滚（保证原子性）+ MVCC 版本链 崩溃恢复（保证持久性）
什么时候用 事务回滚时 宕机重启后

Q3：为什么要有 redo log？为什么写 redo 不直接写 B+ 树？
一句话结论：因为 B+ 树是随机写（要找到页、改页、而且一个页 16KB 改几个字节也要整页刷），redo log 是顺序写——用顺序写换随机写，性能差了几个数量级。这就是 WAL（Write-Ahead Logging）。

  • Why 不直接改 B+ 树：数据页在 Buffer Pool（内存）里改，改完是脏页。如果每次改都立刻把脏页刷到磁盘，会有两个问题：
    1. 随机写：数据页散落在磁盘各处，每次刷盘都要寻道，非常慢。
    2. 写放大：改一行的一个字段，整页 16KB 都得刷。
  • WAL 的做法：改内存里的页 + 把「改了什么」顺序追加到 redo log（顺序写、快），脏页慢慢异步刷。
  • 崩溃恢复怎么保证不丢：事务提交时只要 redo log 落盘了（innodb_flush_log_at_trx_commit = 1），即使数据页还没刷，重启后也能用 redo log 重放把数据补回来。
  • redo log 的持久性靠三样：WAL、顺序追加写、Checkpoint 机制（按 LSN 确定恢复起点，不用从头重放）。

Q4：binlog 和 redo log 的区别？为什么需要两阶段提交？
一句话结论：redo log 是物理日志、在 InnoDB 层、循环写；binlog 是逻辑日志、在 Server 层、追加写不覆盖。两阶段提交是为了保证这两个日志在崩溃恢复时「状态一致」，否则主从会不一致。

redo log binlog
层级 InnoDB 引擎层 Server 层
内容 物理日志（数据页的物理修改） 逻辑日志（写操作，不含 SELECT）
写入 循环写（空间固定，写满覆盖） 追加写（不覆盖，保存全量）
用途 崩溃恢复 主从复制、数据恢复
格式 — STATEMENT（SQL 语句）/ ROW（每行的最终值）/ MIXED
  • 两阶段提交的流程（UPDATE 语句）：
    1. prepare 阶段：写 redo log，状态置为 prepare。
    2. commit 阶段：写 binlog 并落盘 → 把 redo log 状态改成 commit。
  • 崩溃恢复怎么办：重启后扫 redo log，遇到 prepare 状态的记录，就拿它的事务 ID 去 binlog 里查——binlog 里有 = 提交 → 提交；binlog 里没有 = 没写完 → 回滚。
  • 为什么必须两阶段：如果不用两阶段：
    • 先写 redo 再写 binlog：redo 写完崩溃了，binlog 没写。重启后主库有数据，但从库（靠 binlog 复制）没有 → 主从不一致。
    • 先写 binlog 再写 redo：binlog 写完崩溃了，redo 没写。主库回滚了，但从库照 binlog 回放有了数据 → 主从不一致。
    • 两阶段提交 + 崩溃恢复判断，保证了「binlog 写成功」成为事务提交成功的唯一标志。

Q5：关于持久性的两个关键参数？

  • **innodb_flush_log_at_trx_commit**（redo log 刷盘策略）：
    • 1（默认，最安全）：每次提交都把 redo log 刷到磁盘，不丢数据。
    • 0：交给后台线程每秒刷一次，宕机可能丢 1 秒数据。
    • 2：写到操作系统 page cache，宕机（不是断电）不丢，机器断电可能丢 1 秒。
  • **sync_binlog**（binlog 刷盘策略）：
    • 1（最安全）：每次提交都刷 binlog 到磁盘。
    • 0：交给操作系统决定。
  • 生产推荐「双 1 配置」：innodb_flush_log_at_trx_commit = 1 + sync_binlog = 1。代价是每次提交都要两次 fsync，性能会降，但不丢数据是对业务的基本承诺。

Q6：什么是 double write buffer（两次写）？
一句话结论：解决「刷一个 16KB 的数据页时断电，导致页损坏、redo log 也救不回来」的问题。

  • 问题背景：InnoDB 的数据页是 16KB，而操作系统文件系统的一页是 4KB。所以刷一个数据页要写 4 个文件系统页，这个写入不是原子的。如果写到一半断电，数据页就处于「写了一半」的损坏状态。
  • redo log 为什么救不回来：redo log 记录的是「对某个页做了什么修改」的操作日志，它的前提是那个页本身是完好的。页都损坏了，在损坏的页上重放 redo 没有意义。
  • double write 的做法：
    1. 刷盘前，先把页 memcpy 到内存里的一块区域（double write buffer，约 2MB）。
    2. 先顺序写到磁盘上的 double write 区域。
    3. 再从 double write 区域刷到真正的 .ibd 文件（随机写）。
  • 崩溃时的三种情况：
    • 步骤 2 之前崩：数据页没动，redo 可以正常恢复。
    • 步骤 2 之后、步骤 3 之前崩：磁盘上的 double write 区域有完整的页副本，用它覆盖损坏的 .ibd 页，再用 redo 恢复 → 能救回来。
    • 步骤 3 之后崩：数据页完整，无事。
  • 一句话总结：double write 是针对「数据页的原子性」的保证，补的是 redo log 兜不住的那个洞。

1.3.5 MySQL 主从复制与分库分表

Q1：主从复制的原理？
一句话结论：靠 binlog 实现，三个阶段——主库写 binlog → 从库 I/O 线程把 binlog 拉过来写进 relay log → 从库 SQL 线程回放 relay log。

  1. 主库执行写操作，写进 binlog。
  2. 从库的 I/O 线程连上主库，主库的 dump 线程把 binlog 发过来，I/O 线程收到后写进 relay log。
  3. 从库的 SQL 线程读 relay log，在从库上重放这些操作。
  • 默认是异步复制：主库写完 binlog 就返回，不等从库确认。所以主库挂了可能丢数据（还没传过去的 binlog）。
  • 半同步复制：主库等至少一个从库收到 binlog 并 ACK 才返回。比异步安全，但会慢一点。
  • 主从延迟的原因：从库要串行回放主库的并行写入，主库压力大时从库跟不上。大事务会显著放大延迟——主库执行 10 分钟，从库就得回放 10 分钟。
  • 主从延迟的应对：关键业务读主库（比如「用户下单后立刻查订单详情」，不能读从库，否则可能查不到）。

Q2：分库和分表分别解决什么问题？
一句话结论：分库解决「并发连接太多」（数据库连接数被打满），分表解决「单表数据量太大」（查询和写入都变慢）。

方式 解决 说明
垂直分库 业务耦合 按业务拆成不同的库（比如用户库、订单库），专库专用
垂直分表 单表字段太多 把不常用的大字段（如 text）拆到另一张表，提高单页能加载的行数和索引命中率
水平分库 单库并发/容量 同一个表拆到多个库，按某个规则路由（比如 user_id % 2）
水平分表 单表数据量 同库内拆成结构相同的多张子表。注意：仍在一台机器上，还是一起抢 CPU/内存/IO，没有真正分散
  • 水平分表后必须换 ID 生成方案：数据库自增 ID 在多表下会冲突。所以需要分布式 ID（雪花算法、Redis 自增、号段模式）。
  • 代价：跨库 join 做不了（要改成字段冗余或多次查询）、分布式事务、分页排序变复杂、路由规则要小心（分片键选错了会导致查询打散到所有库）。

1.3.6 Redis 数据结构

Q1：Redis 有哪几种数据结构？分别适合什么场景？
一句话结论：五种基础（String / List / Hash / Set / ZSet）+ 四种扩展（BitMap / HyperLogLog / GEO / Stream）。

类型 底层 典型场景
String SDS（简单动态字符串） 缓存对象、计数器（INCR）、分布式锁、共享 Session
List quicklist（3.2+），早期是 ziplist + linkedlist 简单的消息队列（LPUSH + BRPOP）、最新列表
Hash ziplist（元素少时）/ hashtable 存对象（用户信息、购物车），可以单独改某个字段
Set intset（全是整数时）/ hashtable 去重、共同关注（SINTER）、抽奖（SRANDMEMBER）
ZSet ziplist / 跳表 + 哈希表 排行榜、Feed 流时间线、延迟队列
BitMap String（2.2+） 签到、活跃用户统计——每个用户只占 1 bit
HyperLogLog 概率结构（2.8+） UV 基数统计——固定 12KB 存 2^64 个元素
GEO ZSet + GeoHash（3.2+） 附近的人/店
Stream （5.0+） 完整消息队列：全局消息 ID + 消费组 + ACK

Q2：ZSet 的底层？为什么用跳表而不是 B+ 树？
一句话结论：元素数 < 128 且每个元素 < 64 字节时用压缩列表，否则用跳表 + 哈希表。选跳表是因为它实现简单、写性能好、内存无碎片。

  • 双结构：同时维护一个哈希表（member → score，支持 O(1) 查分数）和一个跳表（按 score 有序，支持范围查询和排名）。
  • 跳表是什么：多层有序链表。最底层是完整链表，往上每一层是下一层的「索引」，查找时从最上层开始，大了就往右、小了就往下 —— **查找复杂度 O(log N)**，和平衡树相当，但实现简单得多。
  • 层数怎么定：每个节点随机决定要不要往上加一层，概率 25% 继续加层，最高 64 层。用随机化代替了平衡树的旋转调整。
  • 为什么不用 B+ 树（Redis 作者的回答）：
    1. 内存场景下 CPU 缓存局部性不是瓶颈，B+ 树为磁盘 IO 优化的优势发挥不出来。
    2. 实现复杂度：跳表约 200 行代码，B+ 树要数千行，还要处理节点分裂合并。
    3. 写性能好：ZADD 是 O(log N) 且只改动局部指针，不触发递归分裂。
    4. 内存无内部碎片：B+ 树节点要预留空间，跳表按需分配。
    • 实测数据：跳表插入比 B+ 树快 2~3 倍，查询速度相当。

Q3：Redis 为什么快？
一句话结论：纯内存操作 + 单线程免锁免切换 + I/O 多路复用 + 高效的数据结构。

  1. 内存操作：数据都在内存里，读写不涉及磁盘 IO（这是最主要的）。
  2. 单线程（指命令执行）：没有线程上下文切换开销，没有锁竞争，也不会有死锁。
  3. I/O 多路复用：用 epoll 一个线程监听大量连接，用的是 Reactor 模式。瓶颈在网络 IO，不在 CPU。
  4. 高效的数据结构：SDS、跳表、压缩列表都是为特定场景优化过的。
  5. 官方基准：单线程吞吐量 10 万/秒。
  • 单线程指的是哪一段：从「接收请求 → 解析 → 读写数据 → 发送响应」这条命令执行链路是单线程。Redis 本身其实是多线程的：
    • 2.6 起：2 个后台 BIO 线程（关闭文件、AOF 刷盘）。
    • 4.0 起：新增 lazyfree 线程（大 key 删除用 UNLINK 而不是 DEL，把释放内存放到后台）。
    • 6.0 起：网络 I/O 多线程（因为网络硬件提升了，瓶颈转到了网络 IO），但命令执行依然是单线程。
  • 6.0 的 I/O 多线程要注意：io-threads N 表示启用 N-1 个 I/O 线程（主线程也算一个）；建议 4 核设 2~3、8 核设 6，必须小于机器核数；默认只对发送响应多线程，读请求要多线程得额外开 io-threads-do-reads yes。

Q4：Redis 为什么用单线程还能保证原子性？Lua 是干什么的？
一句话结论：单条命令天然原子（单线程执行期间不会被打断）；多条命令要一起原子，就得用 Lua 脚本——整个脚本在 Redis 里一口气执行完。

  • 单条命令原子：INCR、DECR、SETNX 这些单命令，执行期间没有别的命令能插进来。
  • 多条命令就没有原子性了：GET 完再 DECR，中间可能插进来别的客户端。
  • 为什么不用 Redis 事务（MULTI / EXEC）：
    1. 事务里没有条件分支——只能把命令排队执行，没法在「库存不足时提前 return 打断」。而秒杀恰恰需要在库存为 0 的时候提前返回。
    2. 每次网络往返至少两次（MULTI 一次、EXEC 一次），Lua 只要一次。
    3. Redis 事务没有回滚机制——如果中间某条命令执行出错（比如对 String 执行 LPOP），前面已执行的不会回滚。所以 Redis 事务保证的是「不被其他命令打断」，不是「要么全成功要么全失败」。
  • Lua 的优势：脚本里的多个命令在 Redis 内部连续执行，中间不会有别的命令插进来（单线程特性保证），天然原子；而且只需要一次网络往返。

1.3.7 Redis 持久化

Q1：RDB 和 AOF 的区别？
一句话结论：RDB 是「某一时刻的内存快照」（二进制、体积小、恢复快，但可能丢数据）；AOF 是「追加写命令日志」（数据更完整，但文件大、恢复慢）。

RDB AOF
存什么 某一时刻内存的快照（二进制） 写命令的追加日志
触发 save（阻塞主线程）/ bgsave（fork 子进程，不阻塞）/ 配置的自动触发规则 每条写命令之后，按策略刷盘
体积 小（压缩过的二进制） 大（命令文本，但有重写机制压缩）
恢复速度 快（直接读进内存） 慢（要重放所有命令）
数据完整性 差（两次快照之间宕机会丢数据） 好
对性能的影响 fork 时有开销（copy-on-write） 取决于刷盘策略
  • AOF 的三种刷盘策略：
策略 行为 丢数据 性能
Always 每条命令都 fsync 落盘 不丢 最差
Everysec（默认） 先写内核缓冲区，每秒 fsync 一次 最多丢 1 秒 好
No 完全交给操作系统决定 可能丢很多 最好
  • AOF 重写：AOF 会越来越大（比如一个计数器自增 100 次就是 100 条命令），重写就是根据当前内存状态生成一份最小命令集（100 次自增 → 直接 SET key 100）。重写期间新来的命令会记到重写缓冲区，重写完成后追加进去。
  • 怎么选：生产一般两个都开（aof-use-rdb-preamble 混合持久化）——用 RDB 的格式做 AOF 重写的基底，既有 RDB 的恢复速度，又有 AOF 的数据完整性。

Q2：主从复制的全量同步和增量同步？
一句话结论：全量同步是「主库把 RDB 整个发给从库」，增量同步是「只补发从库断线期间丢掉的那部分命令」；判断依据是 repl_backlog_buffer 里还有没有那段数据。

  • 全量同步三阶段：
    1. 建立连接协商：从库发 PSYNC ? -1，主库回 FULLRESYNC {runId} {offset}（把主库的 runId 和当前偏移量告诉从库）。
    2. 主库 bgsave 生成 RDB 并发给从库，从库清空自己的数据载入 RDB。期间新来的写命令缓存到 replication backlog buffer。
    3. 主库把缓冲区里的新写命令发给从库。
  • 触发全量的场景：初次同步、从库数据丢失、主库数据变化太大（从库的 offset 已经不在 backlog 里了）。
  • 增量同步：断线重连时发带 offset 的 PSYNC，主库判断 offset 之后的数据还在不在 repl_backlog_buffer（环形缓冲区，默认 1MB） 里：
    • 在 → 回 CONTINUE，只把缺的那部分发过去（增量同步）。
    • 已被覆盖 → 只能全量同步（性能损耗大得多）。
  • 优化点：调大 repl_backlog_buffer 能降低断线后触发全量同步的概率。

1.3.8 Redis 过期删除与内存淘汰 ★

这一节必须能一口气讲完——它是「Redis 基础」里最容易露怯的地方。

Q1：Redis 的「缓存过期」机制有哪些？
一句话结论：这是两个不同的机制，要分开说——「过期键删除策略」解决「key 到点了怎么删」，「内存淘汰策略」解决「内存满了怎么腾地方」。

第一个：过期键删除策略（key 到点了怎么删）

Redis 用的是 惰性删除 + 定期删除 的组合。

  • 惰性删除：key 到期后不主动删，等下一次有请求访问到这个 key 的时候，才检查它是否过期，过期就删掉并返回 nil。
    • 好处：对 CPU 友好——没被访问的 key 不浪费 CPU 去检查。
    • 坏处：如果这个 key 再也没人访问，它就会一直占着内存（这是内存泄漏的来源之一，要靠定期删除兜）。
  • 定期删除：Redis 默认每 100 毫秒执行一次（配置项 hz 默认 10，即每秒 10 次），每次从设置了过期时间的 key 里随机抽 20 个，把其中已过期的删掉。
    • 如果这一轮抽出来的样本里，过期 key 的比例超过 25%（也就是抽 20 个有 5 个以上过期），说明过期 key 还很密集，就立刻再来一轮，直到比例降下来。
    • 整个过程有执行时间上限（一个周期内不超过 25 毫秒），到点就停，避免阻塞主线程。
  • 为什么要两个一起用：惰性删除保证「访问时结果一定是准的」、对 CPU 友好；定期删除保证「没人访问的过期 key 也能被清掉」、对内存友好。两者互补，本质是 CPU 和内存之间的折中。

第二个：内存淘汰策略（内存满了怎么腾地方）

  • 触发条件：used_memory 达到 maxmemory 之后，每执行一条命令都会尝试淘汰。
  • 默认策略是 noeviction：不淘汰任何 key，所有写命令直接返回错误 OOM command not allowed when used memory > 'maxmemory'，读命令还能正常用。
  • 一共 8 种，分两族 + 一个不淘汰：
族 策略 淘汰范围
allkeys allkeys-lru / allkeys-lfu / allkeys-random 在所有 key 里挑；lru 挑最久没被访问的，lfu 挑访问频率最低的，random 随机
volatile volatile-lru / volatile-lfu / volatile-random / volatile-ttl 只在设置了过期时间的 key 里挑；volatile-ttl 挑快要过期的
不淘汰 noeviction 默认值，内存满了写命令报 OOM
  • LRU 和 LFU 的区别：LRU 看「最近有没有被访问过」，LFU 看「被访问的频率」。LFU 解决的是「一笔偶尔被扫一次的冷数据把热数据挤掉」的问题——比如一个每天只跑一次的离线任务，扫过一堆 key，如果按 LRU 这些 key 都会被认为是「最近用过」的。
  • 一个加分细节：Redis 的 LRU 不是真正的 LRU，是「近似 LRU」。它不维护完整的访问链表（那要多占大量内存），而是随机采样 5 个 key（maxmemory-samples），比较它们的访问时间戳，淘汰其中最久没被访问的那个。准确率够用，内存省得多。

Q2：项目里 maxmemory-policy 该怎么配？
一句话记法：这个 Redis 实例只做缓存 → allkeys-lru；如果实例里混着不能丢的数据 → volatile-lru，同时保证所有缓存 key 都设了过期时间。

  • 默认的 noeviction 做纯粹的缓存是不能上生产的：内存一满，所有写请求全部失败，业务直接挂。
  • 如果实例里既有缓存又有不能丢的数据（比如存了会话 token），要用 volatile-lru——只淘汰设了过期时间的 key，token 因为没过期时间不会被误删。同时必须保证所有缓存 key 都设了过期时间，否则淘汰范围会空掉。
  • **生产上还要配 maxmemory**（一般设成物理内存的 3/4，留出空间给 fork 时的 copy-on-write 和内存碎片）。

1.3.9 Redis 缓存问题与分布式锁

Q1：缓存穿透、击穿、雪崩的区别和解决？
一句话结论：穿透是「查的数据数据库里根本没有」，击穿是「单个热点 key 过期了」，雪崩是「大批 key 同时过期」。三个问题三个对策。

问题 一句话本质 比喻 对策
穿透 查的数据数据库里根本没有，缓存永远不命中，每次都打到 DB 有人专挑不存在的钥匙开锁 ① 空值缓存（查不到也缓存，TTL 短一点）② 布隆过滤器（在入口就拦掉不存在的 key）③ 参数校验
击穿 单个热点 key 到期那一刻，大量并发同时去查 DB 一把很热的钥匙断了，一群人挤门口 ① 互斥锁重建（只有一个请求去查 DB 并重建缓存）② 热点 key 不设过期 + 后台异步更新
雪崩 大批 key 在同一时刻过期（或 Redis 宕机），请求全部涌向 DB 整栋楼的钥匙同时过期 ① 过期时间加随机值打散 ② Redis 高可用（哨兵/集群）③ 多级缓存 ④ 限流降级
  • 布隆过滤器的原理：一个初始全 0 的位数组 + N 个哈希函数。写入时用 N 个哈希函数算出 N 个位置，全部置 1。查询时同样算 N 个位置——只要有一位是 0，就一定不存在；全部是 1，只能说「可能存在」（因为哈希冲突可能让别的元素把这几位都置上了）。
  • 布隆过滤器 vs 空值缓存：布隆过滤器空间效率极高（一个元素只占几个 bit）、能在入口拦掉，但有误判率（会把存在的判成不存在，也就是「误杀」）且不支持删除；空值缓存实现简单、可以精确判断，但会占内存（被垃圾 key 占着），而且只能挡住「查过的」那些不存在的 key（第一次还是要打到 DB）。数据量小的场景空值缓存就够。
  • 击穿为什么必须加 Double Check：抢到锁之后要再读一次缓存——因为你排队等锁的这段时间，前面拿到锁的线程可能已经把缓存重建好了，你就不用再查一次 DB 了。
  • 击穿的锁为什么必须带 TTL：重建线程如果挂了没释放锁，就是死锁。TTL 保证锁最终一定会被释放。

Q2：缓存和数据库的一致性怎么保证？
一句话结论：以「先更新数据库，再删除缓存」为基准方案；删缓存失败要靠重试或订阅 binlog 兜底，最终做到最终一致。

  • 为什么是「删除」而不是「更新」缓存：更新缓存要处理并发写入的顺序问题（两个请求并发更新，可能是旧值后写入），而且很多缓存值不是简单映射（要算出来），更新成本高。删除更简单——下次读的时候自然从 DB 加载回填。这就是旁路缓存模式（Cache-Aside）。
  • 四种组合的取舍：
方案 问题
先删缓存，再更新 DB 删完之后、更新 DB 之前有并发读，读到旧值并写回缓存 → 留下脏数据，且一直脏 ❌
先更新 DB，再删缓存（推荐基准） 最坏情况只是「删缓存失败」，缓存里留一份旧值，等 TTL 到期自动纠正 ✔
延迟双删 更新 DB 后删一次，睡 500ms 再删一次，覆盖「读请求刚好在删缓存前把旧值写回」的极端时序窗口
订阅 binlog（Canal）异步删缓存 终极方案：Canal 伪装成 MySQL 从库拉 binlog，解析出变更后投 MQ，消费者删缓存 → 做到最终一致
  • 为什么「先更新 DB 再删缓存」也会有窗口：读请求在缓存 miss 后查 DB 拿到旧值，此时写请求更新了 DB 并删了缓存，然后读请求才把旧值写回缓存 —— 缓存里留了旧值。但这个窗口极小（要求读请求在「查 DB」和「写缓存」之间刚好插进一整个写事务），概率上远低于「先删缓存再更新 DB」的方案，所以作为工程基准是够用的。

Q3：Redis 分布式锁的原理？
一句话结论：用 SET key 唯一值 NX EX 秒数 加锁（NX 保证互斥、EX 防死锁、一条命令保证原子），解锁必须用 Lua 先比对唯一值再删除。

按这六步讲：

  1. 加锁：SET lockKey 唯一值 NX EX 10
    • **NX**：key 不存在才设置 → 保证互斥，只有一个客户端能成功。
    • EX：带过期时间 → 防止持锁客户端崩溃导致死锁。
    • 为什么必须合成一条命令：如果分两步（先 SETNX 再 EXPIRE），中间客户端挂了，就是一把永不过期的锁。合成一条命令保证原子。
  2. value 必须是唯一值（UUID、或者「机器 ID + 线程 ID」拼接）：这样解锁的时候能判断「这把锁是不是我加的」。
  3. 解锁必须用 Lua 保证原子： 为什么必须原子：如果分成「先 GET 比对」和「再 DEL」两步，比对完之后锁可能刚好过期并被别人拿到，你再 DEL 就把别人的锁删了。
  4. 锁过期了但业务没做完怎么办：这是单纯 SETNX 方案绕不过去的洞。Redisson 的解法是「看门狗」（WatchDog）——加锁成功后起一个后台定时任务，每隔锁过期时间的 1/3 给锁续期，业务线程结束时主动取消续期。（默认锁 30 秒，每 10 秒续一次。）
  5. 可重入：同一个线程再次加锁应该成功并且计数加一。Redisson 用 Hash 结构存「线程标识 → 重入次数」实现。
  6. 已知的边界（主动说出来，是加分项）：主从切换时会丢锁——主节点加锁成功但还没同步到从节点就挂了，从节点升主之后这把锁就不存在了，别的客户端能重新加锁成功。这个问题的解法是 RedLock（同时向多个独立 Redis 实例加锁，多数成功才算拿到锁），或者干脆换用 etcd / ZooKeeper 这类有共识协议的组件。

Q4：为什么用 Redis 做分布式锁，不用 ZooKeeper / 数据库？

  • Redis：性能最高（内存操作）、实现简单、大多数项目本来就有 Redis。缺点是主从切换可能丢锁。
  • ZooKeeper：靠临时顺序节点，一致性强、不会丢锁，但性能比 Redis 低，而且引入 ZK 是额外的运维成本。
  • 数据库：用唯一索引或 SELECT ... FOR UPDATE 也能做，但性能最差，而且压力全在 DB 上——这跟用缓存挡 DB 流量是矛盾的。
  • 选型逻辑：对一致性要求极高、性能要求不极致 → ZooKeeper；对性能要求高、能接受极小概率的锁失效 → Redis。 秒杀这类场景用 Redis 更合适，因为锁失效的最坏后果是「多人抢到」——而我们还有数据库唯一索引兜底。

1.3.10 Redis 高可用与集群

Q1：Redis 主从、哨兵、集群的区别？
一句话结论：主从解决「读扩展 + 数据备份」（但不自动故障转移），哨兵解决「自动故障转移」（主库挂了自动选新主），集群解决「容量和写扩展」（数据分片到多个节点）。

方案 解决什么 局限
主从复制 读扩展、数据备份 主库挂了要手动切换，写能力还是单机上限
哨兵（Sentinel） 自动故障转移（2.8+） 每个节点还是存全量数据，容量受单机内存限制
集群（Cluster） 数据分片，容量和写能力水平扩展 部署运维复杂；跨节点操作受限

Q2：哨兵的工作原理？
一句话结论：哨兵是一个特殊的 Redis 进程，干三件事——监控、选主、通知。

  • 选主算法四步：
    1. 主观下线：单个哨兵在 down-after-milliseconds 内没收到主库心跳，它认为主库挂了。
    2. 客观下线：这个哨兵去问其他哨兵，超过 quorum 数量的哨兵也认为主库挂了 → 判定为客观下线。（如果是从节点主观下线，到此为止；只有主节点客观下线才触发故障转移。）
    3. 哨兵之间选举 Leader：谁来做故障转移？票数要达到 max(quorum, 哨兵总数/2 + 1) 才能当选。比如 3 个哨兵、quorum = 2，拿到 2 票就当选。
    4. Leader 选新主节点：按顺序筛——先过滤掉不健康的节点，然后选 slave-priority 配置最大的，再选复制偏移量（offset）最大的（数据最全的），最后选 runid 最小的（兜底规则，保证唯一性）。

Q3：Redis 集群的数据是怎么分布的？
一句话结论：16384 个哈希槽，key 用 CRC16(key) % 16384 算出槽号，槽再分配给不同节点。

  • 为什么是 16384：这个数是权衡出来的——槽位信息要在节点之间通过心跳包互相传播（gossip 协议），16384 个槽占 2KB，网络开销可以接受；如果槽数太多，心跳包会变得很大。
  • 槽的分配：redis-cli --cluster create 会平均分配（比如 9 个节点每个 16384/9 个槽）；也可以手动分配（cluster addslots），但必须把 16384 个槽全部分完，否则集群无法工作。
  • 客户端访问错了节点怎么办：节点会返回 MOVED 重定向（槽永久迁移了）或 ASK 重定向（槽正在迁移中）。客户端要根据这些响应重新路由。
  • 局限：涉及多个 key 的操作（比如 SINTER、事务、Lua 脚本里涉及多个 key）要求这些 key 在同一个槽里，否则会报错。解决办法是用 hash tag——user:{1000}:name 和 user:{1000}:age 会因为 {} 里的内容相同而落到同一个槽。

Q4：本地缓存和 Redis 缓存的区别？什么时候用本地缓存？

  • 本地缓存（Caffeine、Guava Cache、Map）：在 JVM 堆内，快、零网络开销，但容量受 JVM 内存限制、多实例之间不一致（每个实例各存一份）。
  • Redis：独立的分布式缓存，容量大、所有实例共享一致的数据，但有网络开销、也要多维护一个组件。
  • 实践：两级缓存——热点数据放本地缓存抗住极高频访问，其余放 Redis。代价是本地缓存的失效同步问题（通常靠 Redis 的发布订阅广播失效通知，或者接受短暂不一致）。

Q5：Redis 的并发能力大概是什么量级？为什么要用 Redis 而不是直接查 MySQL？

  • 一个 4 核 8G 的 Redis 大概能支撑 10 万 QPS（缓存命中的情况下）；而 MySQL 单机大概只能支撑 5000 左右 QPS——差了 20 倍。
  • Redis 比 MySQL 快在哪：① 内存 vs 磁盘；② 简单的键值结构（**Redis 哈希查找 O(1)，MySQL B+ 树查找 O(log n)**）；③ 单线程无锁竞争。
  • 一句话总结：缓存的本质是「牺牲强一致性换取性能」——Redis 主从/集群属于 AP 模型，网络分区时保可用性、牺牲强一致性，但能做到最终一致。

1.3.11 RabbitMQ

Q1：RabbitMQ 的核心组件？
一句话结论：生产者 → 交换机（Exchange）→ 队列（Queue）→ 消费者；中间靠 Binding + RoutingKey 决定消息路由到哪个队列。

组件 比喻 作用
Producer 寄件人 发消息
Exchange 分拣中心 收到消息后按规则路由到队列
Queue 收件柜 存消息，等消费者来取
Consumer 收件人 消费消息
Binding + RoutingKey 派送规则 + 收件地址 决定消息从交换机路由到哪个队列
Broker 邮局 RabbitMQ 服务本身
Channel 一条通信通道 建立在 TCP 连接（Connection）上的虚拟连接，避免频繁建 TCP 连接
  • 为什么要 Channel 不直接复用 Connection：一个 Connection 上可以开多个 Channel，每个 Channel 独立收发消息。TCP 连接的建立成本很高，用 Channel 复用一条 TCP 连接，既能并发又省资源。
  • 一个细节：一个 Channel 里的消息是串行的，如果某个消费者处理慢会阻塞这个 Channel——所以高吞吐场景通常一个消费者用多个 Channel。

Q2：四种交换机类型？
一句话结论：Direct（完全匹配 RoutingKey）、Fanout（广播给所有绑定队列）、Topic（通配符匹配）、Headers（按消息头匹配）。

类型 路由规则 场景
Direct RoutingKey 完全相等才路由 精确投递，比如按订单类型分发
Fanout 广播给所有绑定的队列，忽略 RoutingKey 广播通知——多实例推送、日志分发
Topic RoutingKey 用通配符匹配：*** 匹配一个词，# 匹配零个或多个词** 灵活路由，比如 order.created.cn
Headers 按消息头（headers）匹配，不看 RoutingKey 很少用，性能也差

Q3：怎么保证消息不丢失？
一句话结论：分三层防——生产者到交换机（Publisher Confirm）、交换机到队列（Publisher Return）、队列存储（持久化）、队列到消费者（手动 ACK）；实在处理不了的进死信队列。

环节 机制 配置 作用
生产者 → 交换机 Publisher Confirm publisher-confirm-type: correlated 确认消息到达了交换机
交换机 → 队列 Publisher Return publisher-returns: true + mandatory 路由失败（没有队列匹配）时回调通知，可以重新路由
队列存储 持久化 队列 durable=true + 消息 deliveryMode=2 RabbitMQ 重启消息不丢
队列 → 消费者 手动 ACK acknowledge-mode: manual 处理成功才确认，失败可以重投或转死信
  • 手动 ACK 的重要性：默认的自动 ACK 是「消息一发出去就认为消费成功了」——如果消费者拿到消息还没处理完就崩了，消息就永远丢了。手动 ACK 保证业务处理成功了才确认，消费者崩溃时消息会重新投递。
  • 死信队列（DLX）：三种情况消息会进死信——消息过期、队列满了、消费者 NACK 且不重新入队。死信队列的作用是兜底：这些消息不会消失，可以人工排查、告警、或者定时补偿重试。
  • 一个完整的口径：「三层可靠 + 一层兜底」——confirm（到交换机）、return（到队列）、持久化（不丢盘）、手动 ACK（消费成功），加 DLX 兜底。

Q4：怎么保证消息不重复消费（幂等）？
一句话结论：两层保险——业务层用「状态机」（先查状态，状态不对就直接忽略），数据库层用「唯一键」（重复插入直接失败）。

  • 为什么消息一定会重复：为了保证不丢，就必须有重试（网络抖动、消费者 ACK 丢失、RabbitMQ 重投）。只要有重试，就一定有重复——这是分布式的铁律，所以消费端必须自己保证幂等。
  • 第一层：状态机（挡掉绝大多数）：消费前先查当前状态，用状态判断这个操作该不该执行： 这里的关键是状态判断必须和更新在同一条件里（用 UPDATE ... WHERE status = 1 这种条件更新），不能「先查后改」两步走——两步之间会有窗口。
  • 第二层：唯一键（兜底并发和极端情况）：给业务表加唯一索引。比如支付单表的 order_number 唯一，同一个运单重复建支付单会直接插库失败，捕获异常当成「已处理」返回。
  • 分工：状态机挡掉 99% 的重复消息（性能好、无副作用），唯一键兜住剩下的并发场景（绝对可靠，但会抛异常）。

Q5：延迟消息怎么做？
一句话结论：两种实现——TTL + 死信队列（原生支持，但整个队列只能有一个 TTL），或者延迟交换机插件 rabbitmq_delayed_message_exchange（每条消息可以设不同延迟，但需要装插件）。

方案 怎么做 优点 缺点
TTL + 死信队列 建一个队列设 TTL，消息过期后自动转到死信队列，消费死信队列 原生支持、不用装插件 整个队列只能有一个 TTL，队列里的消息是先进先出的——如果队头消息 TTL 是 30 分钟、后面的是 1 分钟，后面的必须等队头过期才能出来（队头阻塞）
延迟交换机插件（推荐） 用 x-delayed-message 类型的交换机，发消息时用 setDelay(毫秒) 指定延迟 每条消息可以设不同延迟、没有队头阻塞 需要在 RabbitMQ 上装插件（Docker 里靠自定义镜像内置）

Q6：为什么选 RabbitMQ 不用 Kafka 或 RocketMQ？
一句话结论：按需求选——RabbitMQ 轻量、延迟消息成熟、有管理界面；RocketMQ 和 Kafka 吞吐量更高，但那不是这个项目的瓶颈。

RabbitMQ RocketMQ Kafka
吞吐量 万级 十万级 百万级
延迟消息 插件支持 原生支持 不支持
事务消息 不支持 支持 不支持
部署成本 低（一个容器） 中 高（要 ZooKeeper / KRaft）
适用场景 中小规模、复杂路由、延迟消息 大规模、电商核心链路 大数据流、日志采集
  • 选它的理由（问题驱动）：① Docker 部署轻量（一个容器）；② x-delayed-message 插件解决了 30 分钟超时关单这个核心需求；③ 万级的并发量对这个项目完全够用；④ 自带管理界面，排查队列堆积很方便。
  • 主动补边界：「如果订单量到了百万级 QPS，我会重新评估 RocketMQ 或 Kafka」——说出来是加分，说明选型是有判断的，不是只会用这一个。

Q7：消息队列在这个项目里干了哪几件事？
一句话记法：四件事——支付成功通知、超时自动关单、产品停用清理草稿、WebSocket 广播。

用途 生产者 → 消费者 交换机类型
支付成功更新运单状态 pay-service → trade-service Direct
30 分钟超时自动关单 trade-service → trade-service（延迟消息） 延迟交换机
产品停用后清理相关草稿 product-service → cart-service Direct
WebSocket 多实例广播（防漏发） trade-service → trade-service（所有实例） Fanout
  • 异步解耦的价值：同步调用时，主流程里加一个「发短信（2 秒）+ 写日志（1 秒）」就会把 200ms 的接口拖到 3.2 秒。异步之后主流程 200ms 就返回，短信和日志走 MQ 慢慢处理。
  • 一句话总结 MQ 的三个用途：异步解耦、流量削峰、延迟消息。

1.4.1 Docker

Q1：镜像和容器的区别？
一句话结论：镜像是只读的模板（一层层叠加的分层文件系统），容器是镜像跑起来的实例——在镜像最上面加了一个可写层。一个镜像可以跑出很多个容器。

  • 镜像：只读、分层。每一层是一个文件系统的增量（比如「基础层是 Ubuntu」「第二层装 JDK」「第三层放 jar 包」）。分层的好处是层可以复用——多个镜像共享基础层，占的磁盘空间更少。
  • 容器：在镜像之上加一个可写层。所有运行时的修改（写文件、改配置）都记在这个可写层里，镜像本身不动。容器删掉，可写层也跟着没了（所以数据要放数据卷）。
  • 数据卷（Volume）：把宿主机的目录挂进容器，或者用 Docker 管理的卷。容器删了数据还在，这是数据库容器必须挂卷的原因。

Q2：docker ps 和 docker ps -a 的区别？
一句话结论：docker ps 只看正在运行（Up）的容器；docker ps -a 看所有容器，包括已经退出（Exited）的。

  • 这两个的区别是问得最多的。
  • **容器起不来时第一件事就是 docker ps -a**——看它是不是启动完就退出了。如果状态是 Exited (1)，说明启动就报错了；如果状态是 Up 2 seconds 然后又消失，说明是启动后立刻退出。
  • docker logs 容器名 能看到退出原因（标准输出里的报错）。

常用命令按三组背：

第一组：镜像（镜像是模板，只读分层）

命令 作用

第三组：Compose（项目里用的就是这个）

Q3：-p 8080:8080 冒号两边分别是什么？
一句话结论：左边是宿主机端口，右边是容器里的端口。

  • -p 8080:8080 表示「把宿主机的 8080 端口映射到容器的 8080 端口」，外部访问 宿主机IP:8080 就相当于访问容器的 8080。
  • 两边不一定要相同：-p 80:8080 表示外部访问 80，实际打到容器的 8080。
  • -v /host/path:/container/path 的顺序也是一样：左边宿主机，右边容器。

Q4：为什么要用 Docker 多阶段构建？
一句话结论：把「编译环境」和「运行环境」分开——编译用完整的 Maven/JDK 镜像，运行只需要 JRE + jar 包，最终镜像体积小很多，攻击面也小。

  • 两个关键点：
    1. 多阶段构建：最终镜像里没有 Maven、没有源码、没有 .m2 仓库，只有 JRE 和 jar。体积能从 800MB+ 降到 200MB 左右。
    2. 先 COPY pom.xml 再 COPY 源码（层缓存优化）：Docker 构建时，每一层的结果会被缓存，只要指令和文件内容没变，就直接用缓存。把「下载依赖」放在「COPY 源码」之前，改业务代码时就不会重新下载依赖——构建时间从几分钟缩短到几十秒。这一条项目里真做了，可以讲。

Q5：Dockerfile 里 COPY 和 ADD 的区别？
一句话结论：ADD 支持自动解压压缩包和从 URL 下载，COPY 只做纯粹的复制。一般都用 COPY，因为行为更明确。

Q6：为什么不在容器里看日志文件，而是用 docker logs？
一句话结论：应用的日志默认打到标准输出（stdout/stderr），Docker 会自动收集这些输出，docker logs 直接就能看；如果写到文件里，反而需要 docker exec 进容器才能看，不便于统一收集。

  • 正确的做法是应用日志输出到 stdout，由 Docker 的日志驱动收集，再交给 ELK / Loki 统一管理。
  • 容器的最佳实践是「一个容器一个进程、日志走标准输出、状态放数据卷、配置走环境变量」。

用途 具体做什么 为什么交给 AI

Q2：为什么不把核心逻辑也交给 AI？
一句话结论：因为面试官问的是「你为什么这么设计」，AI 生成的代码答不出「为什么」，而且出问题时我不知道从哪下手排查。

  • AI 能写「怎么做」，写不出「为什么这么做」。比如秒杀的 Lua 脚本，AI 可以生成一段扣库存的脚本，但它不会告诉你：
    • 为什么不能用 MULTI/EXEC 事务（因为事务里没有条件分支，库存不足时没法提前 return）；
    • 为什么库存初始化必须用 SETNX 而不是 SET（SET 会把实时库存重置回初始值，直接超卖）；
    • 为什么数据库唯一索引只能防一人多单，防不住 Redis 重启后的超卖（这个边界 AI 不会主动提）。
  • 出了线上问题，只有自己设计的方案才知道从哪查。如果一个模块是 AI 写的、我只知道「能跑」，那它半夜出故障时我没有任何抓手。

Q3：用 AI 写出来的代码，你怎么保证质量？
一句话结论：三件事——约束输入、人工 review、跑验证。

  1. 约束输入：给它明确的上下文（表结构、已有的代码风格、错误码约定），而不是一句话糊上去。上下文给得越准，生成的东西越可用。
  2. 人工 review：每一段 AI 写的代码我都要能讲清楚——它做了什么、有没有边界问题、和现有代码风格是否一致。讲不清的就不合进去。
  3. 跑验证：功能层面用并发测试验证（比如秒杀就是 20 并发验证 0 超卖），而不是「看起来对」。
  4. 我有一份开发日志，记录了每个模块哪些部分是 AI 辅助的、哪些是自己设计的——这个习惯让我对每个模块的「来龙去脉」是有底的。

⚠️ 一个必须守住的底线：涉密和内部数据不进任何外部 AI 工具。 面向政府、金融这类客户的岗位会明确提这条合规红线（我在面试里就遇到过），要正面接住：本地能解决的本地解决，不把代码和数据往外发。

Q4：怎么看待 AI 对开发岗的影响？

「我的判断是：AI 把『写代码』这件事的门槛降低了，但它没有降低『判断该写什么、写完对不对、出问题怎么查』的门槛——后面这三件事反而变得更重要了。

因为它能快速生成大量代码，所以鉴别能力比生成能力更稀缺：一段代码写得好不好、有没有并发问题、边界在哪，需要你自己有判断力才能看出来。这也是我为什么一直在补基础——基础不牢的话，AI 生成的东西是对是错我都看不出来，那就不是在用工具，是在被工具牵着走。」

2.1.1 全局唯一 ID 生成器

是什么
一个不依赖数据库自增的 ID 生成器：41 位时间戳 + 32 位自增序列，用 Redis 的 INCR 产出自增序列。

为什么

  • 不能再用数据库自增：一旦分库分表，两张表的自增 ID 会撞车。而且自增 ID 有规律（能被推算量级），对外暴露也不安全。
  • 为什么不用雪花算法（Snowflake）：雪花算法依赖机器时钟，时钟回拨会产生重复 ID——这是它最著名的坑。Redis 自增不依赖时钟，天然规避。
  • 为什么按天分 key：序列号每天从 0 开始（单天单业务能出 42 亿个 ID），key 自带日期，方便排查，也方便按天清理。

怎么做

  • 为什么用位运算拼接：<< 和 | 是 CPU 一个时钟周期就能完成的操作，比字符串拼接快得多，而且拼接结果可逆（高 32 位是时间、低 32 位是序列），需要时能反解出生成时间。

可能被追问

  • 「ID 的位数是多少？」 → 41 + 32 = 63 位，正好是 long 的正数范围（long 是 64 位，最高位当符号位不用），不会溢出成负数。
  • 「Redis 挂了怎么办？」 → 诚实答：引入了对 Redis 的强依赖，这是这个方案相对雪花的代价。生产上要么给 Redis 做主从/哨兵，要么降级到号段模式（一次取 1000 个 ID 缓存在本地，用完再取）。
  • 「为什么不用 UUID？」 → UUID 是字符串，占空间大、无序。无序意味着作为主键插入 B+ 树时会不断触发页分裂和随机写，性能差；而且 UUID 不可读、不可排序。

2.1.2 签到：BitMap

是什么
用 Redis 的 BitMap 存签到状态——每一位（bit）代表一天签没签到，一个用户一个月只占 31 bit（4 个字节）。

为什么

  • 省空间是压倒性的理由：
方案 存一个用户一个月的签到 相对开销
关系表 一条记录最少几十字节 × 31 天 基准
Set 存日期字符串 "2026-08-01" 这种字符串 × 31 天 上百字节
BitMap 31 bit = 4 字节 省 3~4 个数量级
  • 签到是非常典型的「海量布尔值」场景——每个人每天的状态只有「签了 / 没签」两种，用位图是最贴合的。而且 Redis 的 SETBIT / GETBIT 是 O(1)，性能也好。
  • 「连续签到天数」是个高频需求（签到奖励要按连续天数额度发放），BitMap 也天然支持这个计算。

怎么做

连续天数怎么算（这是个加分点，很多人只会存不会算）：

  • 注意口径：上面这种写法数出来的是「从本月 1 号开始连续签到的天数」——这是月度连续签到奖励最常用的口径（每月 1 号清零重算）。
  • 如果要数「截止到今天连续签到了几天」（比如显示「你已经连续签到 7 天了」，跨月也要连上），就要从高位（今天）往低位数，而且数完当前月还要读上个月的 key，从月末往前接着数。两条口径不一样，面试时要说清你算的是哪一个。
  • **为什么用 BITFIELD 而不是循环 GETBIT**：BITFIELD 一条命令把整段位图取回来，循环 GETBIT 就是 N 次网络往返。

可能被追问

  • 「为什么 key 要按月分而不是一年一个 key、或者一个人一个 key？」 → 按月分是粒度和清理成本的折中：一年一个 key 会让位图变长（365 位），而且跨年要处理偏移；一个月一 key 时 offset 就是「几号 - 1」，计算简单直观，key 也方便按需清理。
  • 「跨月的连续签到怎么算？」 → 当前 key 里数完连续 1 之后，如果数到的天数正好等于「今天是几号」，说明这个月从 1 号开始连续签到，需要再读上个月的 key，从月末往前接着数。这是个边界，要能说清楚。
  • 「为什么不用位运算以外的结构？」 → 位图是「海量布尔值」的最优解，但如果除了签到还要存签到时间、签到地点、签到设备这类信息，位图就不够了，得用关系表。结构选择永远看要存的信息维度。

2.1.3 统计：HyperLogLog 算 UV、INCR 算 PV

是什么

  • PV（Page View）：帖子被浏览的总次数（不去重，同一个人看 10 次算 10 次）。
  • UV（Unique Visitor）：帖子有多少个不重复的访客（要去重）。

为什么

  • PV 用 INCR 就行——它就是个计数器，累加，O(1)。
  • UV 才是难点：如果用一个 Set 存访客 ID，一百万个访客要几十 MB 内存——因为要存下所有元素本身。
  • HyperLogLog 解决的就是这个问题：它是一个基数统计的概率结构，固定占 12KB 内存，跟元素个数完全无关，能在 2^64 个元素规模下把误差控制在 **0.81%**。
  • 为什么可以接受误差：UV 这个指标本身就不需要精确到个位数——「大概有 100 万人看过」和「1000037 人看过」对业务决策没有区别。用 0.81% 的误差换掉几个数量级的内存，这笔交易划算。

怎么做

可能被追问：HyperLogLog 的底层原理（这道题必须能答）

「HyperLogLog 解决的是基数统计——估算一个集合里有多少个不重复元素。注意它不是去重，也不能判断某个元素在不在，它只回答『大概有多少个不同的元素』这一个问题。

原理来自伯努利实验：抛硬币，记录『第一次抛出正面时一共抛了几次』。这个次数越大，说明试的次数越多；反过来，如果记录到的最大值是 k，就能反推实验次数大概是 2 的 k 次方。

具体到算法：把每个元素哈希成一个 64 位串；用低 14 位决定放进哪个桶——所以有 2^14 = 16384 个桶；用剩下位里第一个 1 出现的位置（也就是前导零个数 + 1）作为这个桶的 k 值；每个桶只存自己见过的最大值。

估算的时候，16384 个桶的值取调和平均数——不是算术平均，因为算术平均很容易被一个极端大的值带偏，调和平均对异常值不敏感——再乘一个修正常数。

误差是算出来的：理论标准误差 ≈ 1.04 / √16384 ≈ **0.81%**。

内存是 16384 × 6 bit = 12KB，固定 12KB，这才是它相对 Set 的全部意义所在。」

2.1.4 热榜热搜：ZSet + 定时快照

是什么
三张排行榜：热帖榜、热吧榜、热搜词，全部用 Redis 的 ZSet 实现。

为什么用 ZSet

  • ZSet 就是为排行榜设计的：每个元素有一个 score，Redis 按 score 自动排序，取 TopN 用 ZREVRANGE，复杂度 **O(log N + M)**（M 是要取的条数）。
  • 如果自己用数据库做：ORDER BY score DESC LIMIT 10 每次都要全表排序，数据量一大就慢；而且热度分是频繁变化的（每次浏览/点赞都变），每次变化都 UPDATE 一次数据库，写压力无法承受。

怎么做

榜单 Key score 怎么算 更新方式
热帖榜 dbd:rank:hot:post 浏览 + 点赞 × 2 + 楼层 × 4 @Scheduled 每 5 分钟全量重算
热吧榜 dbd:rank:hot:bar memberCount 定时重算 + 关注时实时 ZADD
热搜词 dbd:search:hot 搜索次数 每次搜索实时 ZINCRBY +1
  • 为什么热帖榜要「定时重算」而不是「实时算」：榜单纯读场景，如果每次有人访问榜单都实时聚合全表，成本极高。定时快照 + 懒构建（榜单 key 为空时立即构建一次）是新鲜度和成本之间的平衡。
  • 为什么热搜词反而用实时 ZINCRBY：因为搜索是低频操作（相比浏览），而且热搜要的就是「实时上升」的感觉，延迟 5 分钟就失去意义了。同一个项目里两种更新策略并存，是因为两个场景的写入频率和实时性要求不同——这个对比本身就是个加分点。
  • 懒构建兜底：和 Feed 流一样，如果榜单 key 不存在（比如 Redis 重启了），第一次访问时立即从数据库重建，而不是等下一个 5 分钟的定时任务，避免用户看到空榜单。
  • 权重为什么要人工设（浏览 ×1、点赞 ×2、评论 ×4）：不同互动的「成本」不一样——浏览是零成本，点赞要一次点击，评论要打字。权重反映的是「用户投入了多少」，投入越多说明内容越有价值，所以评论的权重最高。

2.1.5 同城帖子：GEO

是什么
用户发帖时带上经纬度，能查「附近 N 公里内的帖子」，用 Redis 的 GEO 结构实现。

为什么

  • GEO 底层就是 ZSet + GeoHash——把经纬度交错编码成一个数（GeoHash），编码后地理位置越近的点，编码前缀越像。所以「附近的人/帖子」本质上是 ZSet 的范围查询，Redis 复用了已有的数据结构，不需要引入 ES 或 PostGIS。

怎么做

可能被追问：「为什么用 GEORADIUS 而不是 GEOSEARCH？」
「这是一个版本兼容的取舍。 GEOSEARCH 是 Redis 6.2 才有的新命令，功能更全（同时支持按矩形和圆形搜索）；GEORADIUS 从 3.2 就有，兼容性更好。我的环境是 Redis 5.0，实测不支持 GEOSEARCH，所以我选了 GEORADIUS，并在代码注释里标注了『6.2+ 可以升级到 GEOSEARCH』。根据实际环境做兼容选型，比无脑用最新 API 更重要。」

2.1.6 会话管理：Redis token 而不是 JWT

是什么
登录后生成一个 UUID 作为 token，value 存 userId，存在 Redis 里，30 分钟过期；每次请求命中 token 就续期（滑动过期）。

为什么不用 JWT

  • JWT 是无状态的——服务端不存任何东西，靠签名验证。好处是天然支持分布式；但致命的缺点是无法主动失效：用户点了「退出登录」、管理员封了一个账号、用户改了密码，JWT 在过期之前依然是有效的。
  • Redis 会话可以随时删除——想踢人就 DEL 掉那个 token 的 key，立刻生效。这个项目里需要「退出登录」和「封号」的能力，所以必须用有状态会话。
  • 取舍的另一面要主动说：Redis 会话是有状态的，意味着多实例部署时所有实例必须连同一个 Redis——Redis 就成了单点。JWT 没这个问题。所以这是「可控性」和「无状态扩展性」之间的取舍，看业务需不需要主动失效。

怎么做

  • 为什么 value 存 userId 而不是整个用户对象：省空间，而且用户信息可能变化——存整个对象意味着每次改昵称都要同步更新所有会话。存 ID，需要详细信息时按需查库或查缓存。
  • 为什么用滑动过期：30 分钟是「（多久没操作）」的超时，不是「登录后 30 分钟」。用户一直在用就一直有效，停手 30 分钟才失效——这比固定过期体验好得多。

2.2 【简历第 2 条】抢徽章活动（秒杀）

这是简历上排序第二、但含金量最高的一条，必须能完整讲 3 分钟。
简历原文：用 Lua 脚本把「查库存 + 预扣 + SETNX 一人一单」合并成一次 Redis 操作，数据库加唯一索引兜底；异步落库，失败回补库存。

2.2.1 这个场景到底难在哪？

三个必须解决的问题：

  1. 超卖——库存 100，结果卖出去 137 个。
  2. 一人多单——同一个用户狂点按钮，抢到好几个。
  3. 数据库被打爆——1000 人同时抢，请求全打到 MySQL，数据库连接池被占满，连正常用户的登录、看帖都被拖死。

为什么会有超卖（要能讲清根因）：

「读—判断—写」这三步之间有时间窗口，并发时窗口重叠，判断就全部失效了。根本原因是这三步不是一个原子操作。

2.2.2 演进路线（讲思考过程，面试官最想听这个）

版本 方案 为什么不行
v1 收到请求直接查数据库扣库存 超卖 + 数据库被打爆
v2 synchronized 锁方法 单机有效，多实例部署直接失效；而且锁粒度太粗，把所有请求串行化了
v3 数据库悲观锁 SELECT ... FOR UPDATE 不超卖了，但压力全压在数据库上，秒杀场景下数据库就是瓶颈
v4 数据库乐观锁 UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0 比 v3 好（不用一直持锁），但所有请求还是都要打到数据库
v5 Redis 单命令原子操作（DECR） 单步操作在 Redis 单线程下天然原子，但「判库存 + 判重 + 扣减」是多步，还是会出问题
v6 Lua 脚本（最终方案） ✅ 多步操作合并成一次网络往返，在 Redis 内部一口气执行完
  • v2~v4 没解决的核心问题：它们都在用「更强的锁」解决「并发正确性」，但没有解决「流量根本没到数据库这一层」的问题。 正确思路是把判断和扣减挪到 Redis，让数据库只承接「真正抢到的那 100 个请求」。
  • v5 为什么还不够：Redis 单命令原子，但「判断库存 > 0 → 写一人一单标记 → 扣减库存」是三条命令，中间依然可能被其他客户端的命令插进来。要的是「多条命令的原子性」，只有 Lua 能给你。

2.2.3 核心实现：Lua 脚本

为什么用 Lua，不用 Redis 事务（MULTI / EXEC）？

  1. 事务里没有条件分支——MULTI/EXEC 只能把命令排队执行，没法在「库存不足时提前 return 打断」。而秒杀恰恰最需要这个：库存为 0 时应该立刻返回「售罄」，而不是继续往下走。
  2. 网络往返次数——Lua 一次往返，事务至少两次（MULTI 一次、EXEC 一次）。
  3. Redis 事务没有回滚——中间某条命令执行出错，前面已执行的不会回滚，这跟我们要的「要么全做要么全不做」不是一回事。

Lua 脚本的四步（resources/lua/seckill.lua）：

为什么这段脚本能保证原子：

  • Redis 执行命令是单线程的（6.0 之后网络 IO 多线程，但命令执行依然是单线程）。整个 Lua 脚本在 Redis 里是一口气执行完的，中间不会有任何别的客户端的命令插进来。
  • 所以 1000 个并发请求的脚本会排队串行执行：第 1 个把 100 减到 99，第 2 个把 99 减到 98……第 100 个把 1 减到 0，第 101 个读到的库存是 0，直接返回「库存不足」。全程不会超卖。
  • 只花一次网络往返：4 个步骤在客户端看来就是一次 EVALSHA 调用。

Java 侧怎么调：

库存是什么时候写进 Redis 的？

  • 在 grab() 里做惰性预热：SETNX dbd:seckill:stock:{activityId} 活动库存。只有 key 不存在才初始化。
  • 为什么必须用 SETNX 而不是 SET：如果用 SET，每次有人抢购都会把库存重置成活动配置的初始值——已经把库存卖到 50 了，一重置又变回 100，直接超卖。SETNX 保证只在第一次初始化，后续不会覆盖正在进行的实时库存。

2.2.4 一人一单的双保险

Redis 层：SETNX dbd:seckill:order:{activityId}:{userId} —— 原子标记，并发下只放行一次。

数据库层：activity_order 表的**联合唯一索引 uk_activity_user(activity_id, user_id)**。

为什么需要数据库这层兜底：

  • Redis 是缓存，不是可靠存储。 极端情况下（Redis 重启且没做持久化），一人一单的标记会全部丢失，用户就能重复抢。
  • 数据库唯一索引是最后一道防线——即使 Redis 挂了，重复插入也会因为唯一键冲突直接失败。

为什么唯一索引是「活动 ID + 用户 ID」这两列？

  • 单看 activity_id：一个活动下面有很多人下过单，它不唯一。
  • 单看 user_id：一个人参加过很多活动，也不唯一。
  • 只有这两列放在一起，语义才是「这个人在这个活动里的那一单」——它才唯一。
  • 插入第二条时数据库直接抛主键冲突异常，落库那一步捕获这个异常，把这次抢购当成失败处理。

这套双保险的边界（主动说出来，是加分项）：

「我要说清楚它的局限：这个方案只能防住一人多单，防不住 Redis 重启之后的超卖。 因为 Redis 重启后库存 key 没了，下次有人来抢会用活动配置的初始库存重新初始化——比如配的是 100，之前已经卖出 30 个，它不知道，又从 100 开始卖，最后可能卖出 130 个。要解决这个必须靠对账任务——以数据库已经落库的订单数为准，定期回填 Redis 库存。这个我项目里没做，是已知的缺口。」

2.2.5 异步落库 + 失败补偿

怎么做（SeckillOrderPersistService）

为什么要异步落库：

  • 秒杀接口的响应时间是用户能直接感知的。同步写库要几百毫秒（还要处理唯一索引冲突、可能的行锁等待），而 Redis 预扣只要约 1ms。把这些慢操作移到后台，接口响应从几百毫秒降到十几毫秒，用户体验和吞吐量都大幅提升。
  • 更重要的是：异步之后，落到数据库的只有「真正抢到的那些请求」（100 个库存就只有 100 次写），数据库压力从「1000 次写」降到「100 次写」。

为什么补偿必须是「库存回补 + 删标记」两个动作：

  • 只回补库存、不删标记 → 用户虽然没抢到，但标记还在，他永远不能再抢了（被永久挡住）。
  • 只删标记、不回补库存 → 库存白少了一个，少卖。
  • 两个必须成对做，才构成一个完整的「撤销」。

补偿的边界（必须主动说）：

「这套 try-catch 补偿 + 数据库唯一索引兜底，能覆盖『Redis 正常、数据库偶发故障』这一类问题。但我必须承认一个边界：如果补偿本身也失败了（比如补偿时 Redis 也连不上），那就没有兜底了——库存和数据库会不一致。生产级的做法是引入 MQ 重试加对账任务，把落库失败的消息投进 MQ 反复重试，再用定时任务比对「Redis 扣减量」和「数据库订单数」，发现差异就人工或自动修复。这个我项目里没做，但我知道该怎么做。」

2.2.6 数据口径（★ 不要报没有实测背书的数字）

只说我验证过的：

验证项 口径
功能验证 20 个并发，1 单成功、19 次被拦（返回 4003）、0 超卖

为什么 20 个并发能说明问题（这个解释很重要，否则面试官会觉得你没做压测）：

「我要说明一下这是功能验证不是性能验证。它验证的是逻辑对不对——会不会超卖、会不会一人多单、扣减是不是原子的。这一类问题跟并发量没关系，只要有两个线程同时进来就可能出问题，所以二十个并发足够暴露。性能验证看的是另外的东西：吞吐量、响应时间的分布、错误率，还要定位瓶颈在哪——是 Redis 的网络往返、数据库写入、还是异步线程池排队。这些必须用 JMeter 这类工具持续加压跑一段时间，再配监控看指标才敢下结论。我没有压测工具也没有监控数据，所以不报那个数字。」

2.2.7 秒杀的追问清单

追问 怎么答
抢楼活动楼层号怎么算？ floorNo = 总库存 - 剩余库存，也就是「第几个抢到」。徽章活动不返回楼层（徽章不需要排名序号）。

2.3 【简历第 3 条】缓存体系：穿透 / 击穿 / 雪崩

简历原文：空值缓存防穿透，互斥锁 + Double Check 防击穿，随机过期时间防雪崩（把过期时间打散，避免请求同时打到数据库）

2.3.1 先给结论表

问题 一句话本质 比喻 本项目对策
穿透 查的数据数据库里根本没有，缓存永远不命中 有人专挑不存在的钥匙开锁 空值缓存（5 分钟）
击穿 单个热点 key 到期瞬间，大量并发同时查库 一把很热的钥匙断了，一群人挤门口 SETNX 互斥锁 + Double Check 重建
雪崩 大批 key 在同一时刻过期 整栋楼的钥匙同时过期 随机 TTL（基础 10 分钟 + 0~5 分钟随机）

实现全部集中在 PostServiceImpl 的 readCache() / writeCache() / detail() 里。

2.3.2 穿透：空值缓存

是什么：查不到的数据，也往缓存里写一个空值，并且 TTL 设得更短（5 分钟）。

为什么：

  • 不缓存空值的话，一个恶意请求反复用不存在的 id 查询，每次都会穿透到数据库。如果同时用几万个不存在的 id 打过来，数据库直接被打爆。
  • 缓存一个空值，同一个 id 的后续请求全部在缓存层被挡住，只付一次数据库查询的代价。

怎么做：

为什么空值缓存的 TTL 要比正常 TTL 短：

  • 正常缓存的 TTL 是 10~15 分钟；空值是 5 分钟。
  • 这是为了让「刚被误判为空的数据」尽快恢复。典型场景：用户 A 请求一个还不存在的帖子 id（帖子还没发布），缓存了空值；结果 1 分钟后帖子真的发布了，但因为缓存里有空值，所有人看到的都是「帖子不存在」——一直到 TTL 到期。TTL 短一点，这个错误窗口就短一点。
  • 更深一层：如果帖子发布时主动删掉这个空值缓存，就没有这个问题——但项目里没做这个联动，所以选择用短 TTL 降低影响。

可能被追问：为什么不用布隆过滤器？
「两者是不同层次的方案，我选了空值缓存，原因是场景和数据量。

  • 空值缓存：实现简单（就是往 Redis 写个空串），精确（不会误判），但第一次攻击依然会打到数据库，而且会占内存（被这些垃圾 key 占着）。
  • 布隆过滤器：空间效率极高（一个元素只占几个 bit），能在进入数据库之前就拦掉不存在的请求（连 Redis 都不查），但有误判率——它可能把存在的判成不存在（误杀正常请求），而且不支持删除（要删除得用计数布隆过滤器或定期重建）。
  • 我的选择逻辑：这个项目数据量小、攻击风险低，空值缓存够用，而且没有误判风险（不会误杀正常请求）。如果数据量到了百万级以上、或者担心内存被垃圾 key 占满，就应该上布隆过滤器。」

2.3.3 击穿：互斥锁 + Double Check 重建

是什么：缓存 miss 之后，只允许一个线程去查数据库重建缓存，其他线程等待或直接返回。

为什么：

  • 热点 key 到期的那一刻，假设有 1000 个并发请求同时发现缓存 miss，它们会一起去查数据库——这不是「一个请求查一次」，而是「1000 个请求查 1000 次同样的数据」。
  • 用锁把并发的 1000 次查库收敛成 1 次，重建完缓存后其他请求直接从缓存拿。

怎么做：

两个细节必须主动讲（这是区分「抄的」和「懂了」的地方）：

① 为什么要 Double Check

「抢到锁之后必须再读一次缓存。因为从『发现缓存 miss』到『抢到锁』之间是有一段时间的——在这段时间里，前面持有锁的线程可能已经把缓存重建好了。不做 Double Check 的话，我会白查一次数据库，锁的意义就打了折扣。」

② 为什么锁必须带 TTL（10 秒）

「因为重建线程如果在持有锁期间挂了（进程被 kill、机器宕机、或者抛了未捕获的异常），锁就永远不会被释放——后面所有请求都拿不到锁，全都走 else 分支去查数据库，缓存彻底失效，这就是死锁。 加 TTL 保证锁最终一定会自动释放。」

③ 为什么没抢到锁的线程要 sleep(50) 然后直查

「这是一个可用性的取舍。更严格的做法是让没抢到锁的线程自旋等待，但那样会把请求线程占住、响应时间不可控。我的做法是等 50ms（给持锁线程一点时间去重建），然后自己直接查库——牺牲一点点数据库压力，换用户的响应时间可控。缓存重建本身是很快的（一次主键查询），50ms 通常够了。」

可能被追问：「为什么锁不用 Redisson？」
「这是按场景做的取舍。 我的两把锁（重建锁 10 秒、防重锁 3 秒）都满足『带 TTL』这一条，而它们的业务执行时间远小于 TTL（重建缓存就是一次主键查询，几十毫秒），所以不需要续期。Redisson 的价值在于：看门狗自动续期（业务执行可能超过锁 TTL 的场景）、可重入、解锁时校验持有者身份。我的项目规模用 SETNX + TTL 够用且零依赖；如果业务耗时不可控，就应该升级到 Redisson。 我知道它是更完善的方案，也知道为什么这里不需要。」

2.3.4 雪崩：随机 TTL

是什么：给缓存的过期时间加一个随机偏移量——基础 10 分钟 + 0~5 分钟随机。

为什么：

  • 如果一批缓存都在同一时刻写入（比如服务刚启动时预热、或者某个批量任务刚跑完），它们的 TTL 完全相同，就会在同一时刻集体过期。那一刻所有请求同时 miss，全部涌向数据库，数据库被打崩——然后应用因为等数据库而堆积线程，连锁雪崩。
  • 打散过期时间，把「一个瞬间的压力」摊平到 5 分钟的时间窗里，数据库承受的瞬时压力就能降几个数量级。

怎么做：

  • 为什么用 ThreadLocalRandom 而不是 Random：Random 内部用 CAS 更新种子，高并发下会有竞争；ThreadLocalRandom 每个线程一个种子，无竞争，性能更好。

可能被追问：「雪崩只有随机 TTL 这一个解法吗？」
「不止，而且要说清楚随机 TTL 解决的是『我自己的一批 key 同时过期』，解决不了『Redis 整个挂了』。完整的雪崩防护是分层的：

  1. 过期时间打散（我做的）——防「同时过期」。
  2. Redis 高可用（主从 + 哨兵 / 集群）——防「Redis 挂了」。这个我项目里没做，是单点。
  3. 多级缓存（本地缓存 Caffeine + Redis）——Redis 挂了还有 JVM 内的缓存兜一层。
  4. 限流 + 降级（Sentinel）——真的全打到数据库了，用限流把流量卡在数据库能承受的量级，超出的请求返回兜底响应。
    我这个项目做了第 1 层，第 2~4 层是我的已知边界。」

2.3.5 缓存一致性（雪崩之外最常被追问的）

本项目的做法：写完数据库后删缓存（旁路缓存模式，Cache-Aside）。

四种方案的一致性阶梯（要能讲出完整的演进）：

方案 问题 评价
先删缓存，再更新 DB 删完之后、更新 DB 之前有并发读，读到旧值并写回缓存 → 留下脏数据，而且一直脏到 TTL 到期 ❌ 不可取
先更新 DB，再删缓存 最坏情况只是「删缓存失败」，缓存里留一份旧值，等 TTL 到期自动纠正 ✔ 推荐基准，项目用的是这个
延迟双删 更新 DB 后删一次，睡 500ms 再删一次，覆盖「读请求刚好在删缓存前把旧值写回」的极端时序 兜底手段，项目里只在注释里写了升级路径，没实现
订阅 binlog（Canal） Canal 伪装成 MySQL 从库拉 binlog → 解析变更 → 投 MQ → 消费者删缓存 终极方案，做到最终一致，项目里没做

「先更新 DB 再删缓存」也会有一致性窗口，为什么还能作为基准：

「确实有窗口：读请求在缓存 miss 后查 DB 拿到旧值 → 此时写请求更新了 DB 并删了缓存 → 读请求才把旧值写回缓存，缓存里就留了旧值。但这个窗口极小——它要求整个写事务（含删缓存）必须在读请求的『查库』和『写缓存』这两个瞬间之间完整地插进去。而『先删缓存再更新 DB』的窗口要大得多（整个 DB 更新过程都在窗口内），所以工程上以『先更新 DB 再删缓存』为基准是合理的。要彻底消除，就得上 binlog 订阅。」

可能被追问：「删缓存失败了怎么办？」
「诚实说：我这个项目没有重试机制。 删缓存失败（比如那一瞬间 Redis 网络抖动）就只能等 TTL 自然过期来纠正——这是最终一致，不是强一致。生产级的解法有两种：① 用 MQ 把删除操作做成可靠消息——删除失败就入队重试，重试超过一定次数就告警，成功则移除消息避免重复；② 订阅 binlog 异步删缓存（Canal），把删除动作从业务代码里彻底解耦，业务只管写库，缓存由独立链路保证。我目前只做到了『知道这两条路线』，代码里没实现。」

2.4 【简历第 4 条】Feed 流

简历原文：ZSet 时间线 + 推模式，游标分页代替 offset，时间线丢失时从关注关系重建

2.4.1 需求是什么

用户关注了若干人和若干吧，打开「关注动态」页时，要看到这些对象发的新帖，按时间倒序，能一直往下翻。

2.4.2 推模式 vs 拉模式 vs 推拉结合

模式 怎么做 优点 缺点
推（写扩散） 发帖时，把帖子 id 写进每个粉丝的时间线 读时零聚合，快（读自己的 ZSet 就行） 发帖时要写 N 个粉丝；大 V 粉丝百万级会写爆
拉（读聚合） 读时现查所有关注对象的最新帖，再合并排序 发帖零成本 每次读都要聚合，关注多时很慢
推拉结合 普通用户推，大 V 拉（读时合并大 V 的最新帖） 平衡 实现复杂

为什么这个项目选推模式：

「论坛场景是读 Feed 远多于发帖的——一个用户可能一天刷十次关注页，但一周才发一条帖。推模式把成本放在低频的写侧（发帖时多写几次），换来读侧 O(1)（直接读自己的 ZSet），完全符合这个读写比。

但我必须说清楚它的边界：如果出现百万粉丝的大 V，写扩散会撑不住——他发一条帖要写 100 万个粉丝的时间线，这一条请求就要几秒甚至几十秒。这时候应该切到推拉结合：普通用户（粉丝数低于阈值，比如 10 万）走推，大 V 走拉——发帖时只写自己的发件箱，粉丝读 Feed 时再单独把大 V 的最新帖合并进来。推拉结合我没实现，这是我主动交代的边界。」

2.4.3 ZSet 时间线怎么设计

为什么用 ZSet：

  • ZSet 有两个关键能力：按 score 自动排序 + 支持按 score 范围查询。Feed 流需要的正是「按时间倒序」和「取某个时间点之前的 N 条」——两者完美对应。

score 和 member 怎么选：

项 选择 为什么
member **postId**（字符串） 只需要能唯一定位帖子；不存整个帖子对象——因为帖子内容会变（被编辑、被删），存进去就要同步更新；只存 id，读的时候按 id 批量查（可以再套一层缓存）
score 发帖时间戳（毫秒） 天然有序，而且毫秒精度能区分同一秒内发的多条帖
  • 内存成本估算（加分细节）：一个 ZSet 元素大约占几十字节（跳表节点 + 哈希表条目）。一个粉丝关注 100 个人、每人每天发 1 条帖，一年就是 36500 条，约 1~2 MB。所以时间线必须裁剪——项目里在 ZADD 之后会 ZREMRANGEBYRANK 掉超出长度的老数据，只保留最近 N 条。

2.4.4 游标分页代替 offset

**为什么不用 LIMIT offset, size**：

  1. 深翻页性能差：LIMIT 1000, 10 不是「跳过 1000 行」——MySQL/Redis 都要先拿出 1010 条，再把前 1000 条丢掉。翻到第 100 页时，每次都要扫一万条数据。
  2. 翻页期间数据变动会导致重复 / 错位：这是更严重的问题。假设你正在看第 1 页（帖子 100~91），此时有人发了新帖（帖子 101）插到最前面，整个列表往后移了一位。你翻到第 2 页时，offset=10 拿到的第一条是上一次第 1 页的最后一条 —— 它重复出现了。反过来如果有人删帖，就会有内容被漏掉。（刷抖音时「翻页看到重复内容」就是这个现象。）

游标分页怎么做：

  • 前端配合：FeedView.vue 用「加载更多」按钮，每次带上上次返回的 lastId。
  • 为什么 lastId - 1 是必要的：ZREVRANGEBYSCORE 的区间是闭区间（包含边界），不减去 1 的话，上一页的最后一条会重复出现在下一页的开头。
  • 复杂度对比：游标分页是 O(log N + M)（先二分定位到 score，再往后取 M 个），跟页数无关；offset 分页的复杂度随 offset 线性增长。而且游标分页天然免疫「插入导致的错位」——因为它不是按位置定位，而是按「时间戳」定位。

2.4.5 时间线丢失时从关注关系重建（本项目亮点）

要解决什么问题：

  1. 推模式只对新发的帖生效——用户关注之前的历史帖子不在时间线里，用户刚关注一个人，会看到空的时间线。
  2. Redis 重启后时间线全丢——如果没做持久化，所有用户的 ZSet 都没了。

怎么做（懒构建）：

为什么用「懒构建」而不是「定时任务全量刷」：

「定时任务的问题是：它会把成本花在没人看的数据上。 一百万个用户，其中只有 10 万活跃，定时任务每次都要刷一百万个时间线。

懒构建的思路是「按需自愈」——只有真的有人来读这个时间线、发现它是空的，才去重建。 这样：

  1. 成本只花在真正被访问的数据上，不浪费。
  2. 天然覆盖了 Redis 重启的场景——重启后所有人第一次访问都会自愈，不需要人工介入。
  3. 对用户是无感的——重建就发生在这次请求里，用户看到的是正常的内容。

代价是第一次访问会慢一点（要读关注关系 + 查 200 条帖 + 批量 ZADD）。但这是一次性的——重建完之后后续访问都是 O(log N)。

同样的『懒构建』思路我在排行榜上也用了：榜单 key 不存在时立即重建，而不是等下一个 5 分钟的定时任务。这是我在这个项目里复用的一套兜底模式。」

边界：只补最近 200 条，更早的历史帖子不在时间线里（用户翻到底就翻不到了）。这是「重建成本」和「数据完整性」之间的取舍。

2.5 【简历第 5 条】部署上线

简历原文：Docker Compose 编排全套服务，healthcheck 控制启动顺序；Nginx 托管前端、反代接口，部署在阿里云服务器上跑通上线

2.5.1 Docker Compose 编排了什么

4 个服务：

服务 说明
mysql MySQL 8，挂载 init.sql 自动初始化
redis Redis，承载秒杀、缓存、Feed、签到等全部 Redis 用途
dbd-server Spring Boot 后端
dbd-web Nginx + Vue3 前端静态资源

2.5.2 为什么需要 healthcheck 控制启动顺序

是什么
在 docker-compose.yml 里给基础设施服务配健康检查，应用服务用 depends_on: condition: service_healthy 等它们真的就绪再启动。

为什么（这是踩过的坑，一定要讲）

「depends_on 的默认行为是只等容器『启动』，不等它『就绪』。结果就是：MySQL 容器已经 Up 了，但 MySQL 进程还在做初始化（建库、灌数据、初始化 InnoDB），要几十秒才能接受连接。这时候后端已经启动，连数据库直接失败，Spring Boot 启动报错直接退出，然后 Docker 按重启策略不断重启它——日志里全是一模一样的连接失败堆栈。

解决办法就是 healthcheck：给 MySQL 配 mysqladmin ping，Redis 配 redis-cli ping，只有健康检查通过，应用才启动。」

怎么做：

几个细节：

  • start_period 很重要——MySQL 第一次初始化要几十秒，不加宽限期的话，前几次检查必然失败，可能被判成不健康。
  • MYSQL_HOST: mysql 用的是 Compose 的服务名——Compose 会给每个服务在内部 DNS 里注册服务名，服务之间直接用服务名互相访问，不用写 IP。
  • 配置外置：application.yml 里全部写成 ${MYSQL_HOST:localhost} 这种带默认值的形式，同一份配置在本地开发（用 localhost）和容器里（用服务名）都能跑，不用改代码。

2.5.3 Nginx 干了三件事

1. 托管前端静态资源

  • try_files ... /index.html 是必须的：Vue 用的是 history 模式，路由是前端用 JS 处理的（/post/123 这种路径服务端并不存在）。如果用户直接访问 http://域名/post/123 或者按 F5 刷新，Nginx 会去找 /post/123 这个文件，找不到就返回 404。try_files 的作用是：找不到就**统一返回 index.html**，让前端路由接管，页面才能正常渲染。

2. 反代后端接口

  • 好处：前端只需要请求同源的 /api/xxx，没有跨域问题（因为对浏览器来说前后端同源）；后端 IP 和端口变化时只改 Nginx 配置，前端不用动。

3. 前端多阶段构建

  • **最终镜像里没有 node、没有源码、没有 node_modules**，只有 nginx 和打包好的静态文件，体积从 1GB+ 降到 20MB 左右。

2.5.4 部署踩过的坑（★★ 这一部分是「真做过」最强的证据，必须准备）

面试官判断你是不是照着视频抄的，很大程度就看你能不能说出「只有真做过才知道」的细节。

坑 1：MySQL 容器起来了但后端起不来

  • 现象：docker compose up -d 之后，MySQL 显示 Up，但后端日志里全是连接失败的堆栈，不断重启。
  • 原因：depends_on 只等容器启动，不等服务就绪；MySQL 容器起来后还要几十秒初始化。
  • 解决：加 healthcheck + depends_on: condition: service_healthy。

坑 2：proxy_pass 带不带斜杠的区别

  • location /api/ { proxy_pass http://backend:8080/; } （带斜杠）：/api/user/1 → 转发成 /user/1（去掉 /api 前缀）。
  • location /api/ { proxy_pass http://backend:8080; } （不带斜杠）：/api/user/1 → 转发成 /api/user/1（保留前缀）。
  • 这个差异不看文档根本不知道，但配错了接口全部 404。 我项目里用的是带斜杠的，让后端的路径不含 /api。

坑 3：docker compose down 删不删数据卷

  • docker compose down 只删容器和网络，数据卷默认保留——所以数据库数据还在。
  • docker compose down -v 会连数据卷一起删——数据库数据全没了。
  • 结论：在服务器上千万不要随手加 -v。 我本地调试时踩过这个，数据全清了一次。

坑 4：端口暴露与安全

  • Compose 只把需要对外的端口映射到宿主机（Nginx 的 80），MySQL 的 3306、Redis 的 6379 不往外映射——否则公网可以直接连你的数据库。
  • 阿里云还要在安全组里放行端口，只放 80（和 22 用来 SSH）。

坑 5：论坛类网站上线要备案

  • 我目前只配置了公网 IP 访问，没有买域名——因为域名解析到国内服务器需要 ICP 备案，个人短时间内办不下来。这一点在自我介绍时主动说清楚，比被问到再解释好。

2.6 项目一收口问题

Q1：这个项目最大的难点是什么？

「难点不在写某个功能，而在于把『听起来简单』的需求做到并发下正确。

比如抢徽章，表面上看就是『查库存、扣库存』。但真做下去会遇到一串问题：读-判-写三步不原子会超卖；加锁的话单机锁在多实例下失效、数据库锁会把压力全压在数据库上；挪到 Redis 之后又发现多步命令之间还是会被插入，最后必须用 Lua；Lua 解决了原子性，又要处理『Redis 成功但数据库写失败』的补偿；补偿写完了，还要承认『补偿本身失败就没有兜底』这个边界。

每一步都是解决了上一个方案的问题、又暴露出新的问题。 这个过程让我理解了一件事：分布式场景下没有『正确』的方案，只有在特定约束下的取舍，而且每个方案都有明确的边界。」

Q2：这个项目的不足 / 可以优化的地方？

「我列四条，都是明确的：

  1. 秒杀补偿没有兜底——catch 里的回补如果也失败，就没有重试机制了。应该引入 MQ 重试 + 对账任务（以数据库为准定期回填 Redis 库存）。
  2. 删缓存失败没有重试——目前只能靠 TTL 自然过期纠正。应该用 MQ 可靠消息或者订阅 binlog 来保证最终一致。
  3. Redis 是单点——没做主从和哨兵，Redis 挂了秒杀 fail-fast、缓存靠懒构建自愈，但可用性没有保障。
  4. Feed 推模式没做推拉结合——大 V 场景会写扩散爆掉，目前只是『知道该怎么做』。
    这四条我都在项目文档里做了标注，是主动列出来的，不是等被问才说。」

Q3：这些项目是照着视频/教程做的吗？AI 占多少？

「我不回避这个问题。

起点确实是跟着教程学的——第一个项目的原型是照着 Redis 的教学项目做的，我一开始的想法就是『把 Redis 的各种数据结构和场景都亲手写一遍』。

3.1.1 「一套后端支撑两端」是什么意思

是什么
同一套后端服务，同时支撑两个完全不同的客户端：

  • 用户端（微信小程序）：C 端用户下单、支付、查进度、看历史订单。
  • 门店端（管理后台）：门店员工录单、接单、发运、看工作台和报表。

为什么这么设计（而不是拆两套后端）

  • 业务逻辑高度重合：用户下单和门店录单，最后都是创建一张运单；用户查进度和门店看运单列表，读的是同一批数据。拆成两套后端等于把同一套业务逻辑写两遍，而且数据一致性极难保证（两边都可能改运单状态）。
  • 两类用户的差异只在「入口和权限」，不在「业务」：所以共用业务层，只在网关做分流、在 Controller 层分包。

怎么做

  1. 网关按路径分流：
    • /admin/** → 走员工身份（门店后台）
    • /user/** → 走用户身份（小程序）
  2. 服务内按包分层：
  3. 分包的取舍：controller/admin 和 controller/user 里的接口长得不一样（返回的字段、鉴权方式不同），但底下调的 OrderService、PaymentService 是同一批。差异隔离在 Controller，业务逻辑只有一份。

可能被追问：「两个端的接口怎么保证不互相干扰？」
「靠网关的路径规则 + 两套独立的 JWT 密钥。员工登录拿到的是 token（放在 token 请求头），用户登录拿到的是 authentication（放在 authentication 请求头），密钥都不一样——员工签的 token 拿到用户端用是验不过的，反之也一样。 这样就从根本上杜绝了『员工凭证访问用户接口』或『用户凭证访问后台接口』。」

（B）拆开的代价（这是最重要的部分，必须主动说）

代价 具体表现 补偿手段
1. 跨库 join 做不了了 以前一句 SQL 能 join 出运单 + 产品名，现在订单库和产品库是两个库 写时冗余快照 + 读时 Feign 聚合（见 3.3）

（C）一句话总结（背下来）

「微服务不是银弹，它把单体的结构问题变成了分布式问题。 单体时所有问题都在一个进程里，你只需要一个 @Transactional；拆开之后，你必须配套四件套才能让系统重新站稳：

  • 契约（sky-api 模块统一 Feign 接口定义）
  • 事务（Seata 强一致 + MQ 最终一致）
  • 保护（Sentinel 限流熔断）
  • 部署（Docker Compose 一键起环境）

少了任何一件，微服务都会变成负资产。」

（D）会不会过度拆分？

「标准是业务边界和独立伸缩性，不是代码量。 我的判断依据是：这个服务有没有独立的业务领域、有没有独立的数据、有没有独立的伸缩需求。

反面例子：我没有把「运单」和「报表」拆成两个服务——因为它们共用同一套状态机，报表统计的就是运单数据。硬拆的话，报表查数据要跨服务调运单，分布式事务和跨库 join 的问题会到处蔓延，收益却几乎没有（报表本身不需要单独伸缩）。

拆分的收益必须大于它引入的复杂度，否则不拆。」

3.1.3 一服务一库：为什么，以及怎么落地

是什么
每个服务有自己独立的数据库，服务只能访问自己的库，跨服务只能调接口，不能直连别人的库。

为什么（三个理由）

  1. 边界靠数据库强制隔离——如果五个服务共用一个库，那所谓的「服务边界」只是口头约定，随时可能有人写一句跨表的 join 把边界撕开。物理上分开库，边界就变成了硬约束。
  2. 慢 SQL 不会互相拖累——报表服务跑一个慢查询，不会把用户登录的库连接占满。
  3. 可以独立扩容和发布——订单库压力大就单独给订单库加配置，不影响别人。

代价与落地规则

  • 代价：跨库不能 join。 这是这条规则唯一但很痛的代价。
  • 落地规则：「跨服务只能通过接口调用（Feign），或者通过 MQ 异步传递数据，绝不允许一个服务连到另一个服务的库上。」

3.1.4 Nacos：注册中心 + 配置中心

是什么
Nacos 在这个项目里扮演两个角色：

  1. 注册中心：服务启动时把自己的 IP:端口注册上去，其他服务通过服务名（如 user-service）找到实例列表。
  2. 配置中心：所有配置存在 Nacos 上，改完立即推送给服务，不用重启。

为什么选它而不是 Eureka + Config

Eureka + Spring Cloud Config Nacos
组件数 两个（注册一个、配置一个） 一个，两个角色
配置热更新 需要额外接 Bus + MQ 才能广播刷新 原生支持，改完即推送
一致性模型 只有 AP 支持 AP/CP 切换
健康检查 只有客户端心跳 心跳 + 服务端主动探测
界面 有 有，而且能直接改配置
  • 一句话：「一个组件解决两个问题，还比两个组件加起来功能多，没有理由不用它。」

配置怎么加载的（要能讲清链路）

为什么需要 bootstrap.yml（鸡生蛋问题）

「这里有个先有鸡还是先有蛋的问题：连 Nacos 需要知道 Nacos 的地址，但地址是写在配置里的，而配置又在 Nacos 上。

解法是 bootstrap.yml —— 它在 Spring 生命周期的最早期加载，专门用来打破这个循环。它里面只放最小必要的信息：服务名、Nacos 地址、激活哪个 profile、要拉哪些共享配置。拿到这些之后，才能去 Nacos 把真正的配置拉下来。」

配置优先级（高低顺序）

  • 口诀：本地 > 远程，服务私有 > 共享。
  • 怎么判断一个配置放哪层：就问一句话——「多个服务用不用？」数据库连接、Redis 地址、JWT 密钥这种大家都用的放 shared-configs；服务自己的端口、自己的库名放 extension-configs。

配置热刷新的原理

流程：Nacos 控制台改配置并发布 → Nacos 推送变更到客户端（长轮询：客户端发请求，服务端 hold 住约 30 秒，有变更立刻返回）→ Spring 刷新 Environment 并发 EnvironmentChangeEvent → RefreshScope 销毁被标注的 Bean → 下次访问用新配置重建。

可能被追问：「热刷新有什么坑？」
「两个：

  1. 不加 @RefreshScope 的 Bean 不会刷新——如果用 @Value 直接注入，改了 Nacos 也不生效，因为值在 Bean 创建时就写死了。
  2. 连接池、线程池这类 Bean 千万不要加 @RefreshScope——刷新会导致连接池重建，线上表现为连接抖动。数据库密码这种需要改的配置，应该配合优雅重启，而不是热刷新。」

3.1.5 OpenFeign：服务间调用

是什么
声明式 HTTP 客户端——写一个接口加注解，用起来像调本地方法，底层自动帮你发 HTTP 请求。

为什么不用 RestTemplate

  • Feign 的三个好处：① 接口即契约，类型安全；② 写服务名而不是 IP，自动做服务发现和负载均衡；③ 可以统一配连接池、日志、降级。

sky-api 模块：契约的单一来源

  • 把所有 Feign 接口定义抽到一个独立模块 sky-api 里，调用方（cart-service、trade-service）和实现方（product-service）都依赖它。
  • 好处：契约只有一份，改一处全同步；调用方不需要了解目标服务的内部包结构。这就是「契约先行」。

Feign 的默认坑：没有连接池

  • Feign 默认用 JDK 的 HttpURLConnection，每次请求新建连接，没有连接池，性能很差。
  • 生产必须换成 Apache HttpClient：

Feign 的降级与降级原则

  • 降级三原则（这个分类很能体现思考）：
调用类型 降级动作 为什么
写操作 抛异常 沉默地失败 = 数据不一致。宁可让用户重试，也不能假装成功
关键读 抛异常 不能返回 null——下游拿到 null 会 NPE，问题会以更难排查的形式爆在别处
统计/展示类查询 返回 0 / 空列表 报表少一行数据可以接受，为此让页面整个报错不值得

/internal/** 为什么返回 403

  • 服务间的接口（如 POST /internal/order/create）只给内部调用，网关对 /internal/** 一律 403。
  • 为什么：这些接口没有鉴权逻辑（它们信任调用方是内部服务）。如果暴露出去，任何人都能直接创建运单。在网关层封死，是最外层也是最有效的一道防线。

负载均衡：Spring Cloud LoadBalancer

  • Ribbon 退役后的官方替代。Feign 调 lb://user-service → 从 Nacos 拿实例列表 → 默认轮询选实例 → 发请求。
  • 实例上下线时 Nacos 会通知，列表自动更新，配置里从不写死 http://ip:port。

3.1.6 敏感信息与环境变量

  • 所有敏感信息不进仓库：JWT 密钥、微信支付商户号/API V3 密钥、OSS AccessKey，一律不写死在代码或 git 里。
  • 做法：配置里写占位符 ${SKY_JWT_ADMIN_SECRET}，实际值通过环境变量（Docker Compose 的 environment 段）注入。
  • 为什么这么做：① 密钥泄露是最严重的生产事故之一，git 历史是永久性的；② 同一份代码在不同环境（本地/测试/生产）用不同配置，不用改代码。

3.2 【简历第 2 条】身份与权限：双套 JWT + 全链路透传 + 防越权

简历原文：Gateway 按路径区分员工 / 用户两套独立密钥的 JWT，验签后把身份以 X-User-Id 全链路透传；业务层不信任前端传来的用户 ID，查询更新强制拼当前用户，阻断水平越权

⚠️ 术语提醒：不要把这个叫「双 token」。「双 token」在业界通常指 access token + refresh token（访问令牌 + 刷新令牌），是完全不同的东西。正确的说法是「网关多身份鉴权（admin / user 双套 JWT）」或者「两套独立密钥的 JWT」。

3.2.1 网关到底干了什么

职责清单（四件事）

职责 说明
路由 /admin/** 路由给后台相关的服务，/user/** 路由给小程序相关的服务
统一鉴权 在网关做 JWT 验签，验过之后把用户身份注入请求头往下传
隔离内部接口 /internal/** 一律返回 403
限流 + 跨域 网关层限流；统一处理 CORS

为什么把认证放在网关统一做（而不是每个服务各做一次）

「不放在网关的话，每个微服务都要：引入 JWT 依赖、配置密钥、写一遍验签逻辑。带来三个问题：

  1. 重复——5 个服务 5 套代码，改一处要改五处。
  2. 密钥泄露面变大——密钥散落在 5 个服务里，每个服务的配置都要保护。
  3. 不一致风险——某天有人改了一个服务的验签逻辑，就会出问题。

放在网关之后：JWT 只解密一次、密钥只在网关一处配置、每个业务服务只需要一个读请求头的拦截器。」

3.2.2 两套 JWT 是怎么区分的

是什么
网关只有一个过滤器 JwtAuthFilter，它按请求路径决定验哪一套密钥：

  • /admin/** → 验员工 token（放在请求头 token 里），密钥是 adminSecretKey，解出 empId。
  • /user/** → 验用户 token（放在请求头 authentication 里），密钥是 userSecretKey，解出 userId。

为什么必须两套密钥

「因为这是两类完全不同的人，权限和生命周期都不一样：

  • 员工是公司内部账号，由管理员创建，账号可能一用好几年，权限是门店级别的。
  • 用户是微信登录的 C 端用户，openid 登录即注册，随时可能注销。

如果用同一套密钥，会出现安全问题——一个 C 端用户如果能拿到（或者伪造出）一个有效签名，他就能用这个签名去访问后台接口。密钥隔离是最彻底的隔离：员工密钥签的 token 在用户端验不过，反之也一样。两套密钥互不知道，从密码学上就隔死了。」

白名单（不需要鉴权的路径）

  • 为什么 /notify/** 必须在白名单：支付回调是微信服务器发过来的，它当然没有我们的 JWT。所以这条路径必须放行——但放行不等于不安全，pay-service 会做自己的验签（见 3.4.5）。

3.2.3 X-User-Id 全链路透传（本项目最值得讲的设计）

要解决什么问题
网关验完 JWT 之后，下游的 5 个业务服务怎么知道「当前用户是谁」？

三种可能的做法对比

方案 问题
每个服务自己再解一次 JWT ① 重复——5 个服务都要配密钥；② 密钥泄露面变大；③ 网关验过一次了，重复解密浪费
网关把用户信息塞进请求体 ❌ 请求体是业务数据，会被业务代码读取和修改，语义混乱
网关把用户 ID 放进请求头（X-User-Id）往下传 ✔ 清晰、无侵入、下游只需一个读头的拦截器

怎么做：四个关键类

类 位置 作用
JwtAuthFilter sky-gateway GlobalFilter，解密 JWT，注入 X-User-Id / X-User-Type
UserContextInterceptor sky-common HandlerInterceptor，读 X-User-Id 存 ThreadLocal
BaseContext sky-common 包装 ThreadLocal<Long> 的工具类，业务代码用 BaseContext.getCurrentId() 取当前用户
FeignRequestInterceptor sky-common RequestInterceptor，从 ThreadLocal 取 userId 注入 Feign 请求头

关键代码

两个必须主动讲的技术点：

  • ThreadLocal 的清理：afterCompletion 里必须 remove()。因为 Tomcat 用的是线程池——如果不清，下一个请求复用到这个线程时，会拿到上一个用户的 ID，这是数据泄露级别的 bug。
  • 跨服务时怎么不丢：ThreadLocal 只在当前线程有效。Feign 调用是另起一个线程发 HTTP 请求，拿不到原来线程的 ThreadLocal。所以需要 FeignRequestInterceptor 从 ThreadLocal 取出来、写回请求头——到下一个服务后，那边的 UserContextInterceptor 再从请求头读出来存进自己的 ThreadLocal。「头 → ThreadLocal → 头 → ThreadLocal」这样一跳一跳传下去。

还有什么好处

  • 解密 1 次（原来每个服务都要解）。
  • 密钥只改一处（原来要改 5 个服务的配置）。
  • 业务代码极简：任何地方 BaseContext.getCurrentId() 就能拿到当前用户。

3.2.4 下游服务为什么还要再校验一次

问题：网关已经验过了，业务服务为什么还要检查 X-User-Id 是否存在？

答案：「网关不是唯一入口。」

「任何人只要知道了业务服务的端口，就能绕过网关直接访问——内网调试、配置失误、或者服务器端口没做隔离。这时候请求里根本没有 X-User-Id（因为没人给它注入），如果业务服务不检查、直接当匿名请求处理，那就是一个完全没有认证的接口。

所以 UserContextInterceptor 的逻辑是『读不到身份就拒绝』——if (userId == null) throw new RuntimeException("用户未登录")。这叫纵深防御，不假设外层防线永远有效。」

★ 追问：「那我把 X-User-Id 改成一个别人的 ID，直接访问服务端口呢？」
「X-User-Id 只是一个普通的 HTTP 请求头，技术上确实可以伪造。 但我这个项目里这么做行不通，原因是网络层就不通：

Docker Compose 只把网关的 8080 和基础设施端口映射到宿主机，5 个业务服务的端口根本不对外暴露。 伪造 header 的请求根本到不了业务服务——它连不上那个端口。

但要诚实说边界：这个防护依靠的是『网络隔离』，属于部署层面的保证，不是应用层面的。在真实的生产环境里，如果服务之间是跨机房、跨网络的（比如 K8s 里 Pod 网络互通），伪造请求头是有可能的。生产级的做法应该再加一层服务间鉴权——比如内部调用带一个只有内部服务知道的 token（/internal/** 接口校验），或者直接用 mTLS（双向 TLS）在传输层做服务身份认证。这些是我知道的加固方向，项目里没做。」

3.2.5 阻断水平越权（这一条是简历亮点）

先把两个概念分清（术语用准，这是加分点）

「**鉴权要解决两个不同的问题：

  • 认证（Authentication）：你是谁？—— 这是双套 JWT 解决的。
  • 授权（Authorization）：你能动哪些数据？—— 这是防越权解决的。**

越权又分两种：

  • 垂直越权：低权限用户干了高权限的事（比如普通用户调了管理员接口）。用网关按路径校验身份类型来防（/admin/** 必须带员工 token）。
  • 水平越权：用户 A 用自己的登录态操作了用户 B 的数据（同一权限级别，但不是自己的数据）。这是最常见也最容易漏的一种。」

水平越权是怎么发生的

  • 根因：接口把「用户是谁」这个问题托付给了前端。 而前端是完全不可信的——攻击者可以随意构造请求。

三层堵死（怎么做）

第一层：身份可信（源头）

  • userId 只从 JWT 里解出来，由网关注入 X-User-Id。前端传的任何 userId 参数一律忽略。

第二层：业务圈定（核心）

第三层：跨服务透传（一致性）

  • Feign 调用下游时也带 X-User-Id，下游服务同样执行「强制拼当前用户」。
  • 为什么这一层必要：如果只在上游服务做了圈定，下游服务如果也有暴露的接口，还是会被绕过。每个服务都必须独立地圈定用户维度。

一句话总结（要背下来）

「双 token 解决认证（你是谁），防越权解决授权（你能动哪些数据）。核心原则是：永远不信任前端传来的用户 ID，身份只能来自 JWT；所有查询和更新都必须强制拼上当前用户 ID 作为条件。」

可能被追问：「更新的时候为什么要用条件更新，而不是先查后改？」
「因为『先查后改』中间有窗口。查到的时候是 A 用户的订单，改的时候可能是另一个请求已经把它改掉了，或者更糟——两次操作之间权限状态变化了。条件更新（UPDATE ... WHERE id = ? AND user_id = ?）把『校验』和『修改』合并成一条原子 SQL，要么改成功，要么影响行数是 0（说明不是他的或者不存在），一步到位。」

3.3 【简历第 3 条】跨库一致性：Seata AT + 快照冗余

简历原文：下单要同时动两个库，核心链路用 Seata AT 保证一致；列表页的跨库 join 改成下单时字段快照冗余 + 批量查询，一页只调一次下游、避免循环单条查询

3.3.1 问题是怎么出现的

单体时代：一个 @Transactional 管住所有 SQL——orderMapper.insert + orderDetailMapper.insertBatch + cartMapper.deleteAll，任一步失败，全部回滚。

微服务时代（下单链路）：

  • 数据撕裂的场景：如果 ⑤ 执行成功了，但 ③ 抛异常回滚了 —— 运单没有了，但用户的寄件清单已经被清空。用户的清单凭空消失，而且没有任何记录说明它去哪了。
  • 本地事务保护不了跨库的这几步，因为 @Transactional 只能管住一个数据源。

3.3.2 Seata 是怎么解决这个问题的

（A）三个组件（TC / TM / RM）

组件 全称 谁来当 职责
TC Transaction Coordinator Seata Server（独立部署的 Docker 容器） 协调全局事务的注册、提交、回滚
TM Transaction Manager 发起事务的微服务（trade-service） 标记全局事务的起点和终点，向 TC 开启/提交全局事务
RM Resource Manager 参与事务的每个微服务 管自己的数据库，写 undo_log，响应 TC 的指令

执行流程：

（B）AT 模式的两阶段

  • 阶段一：TM 向 TC 开全局事务（拿 XID）→ trade 本地事务插 orders 并写 undo_log、cart 本地事务更新清单并写 undo_log → 各分支的本地事务先各自提交（注意：AT 是一阶段就提交，这也是它比 XA 性能好的原因）。
  • 阶段二：全部成功 → TC 通知异步清理 undo_log；任一失败 → TC 通知回滚，按 undo_log 生成反向 SQL 把数据改回去。

（C）undo_log 表（每个参与事务的库都要建）

  • 这是 Seata 唯一要求你手动建的表——其余都是自动的。
  • 它的内容就是「怎么撤销这一步」：比如执行了 UPDATE stock SET count = 90 WHERE id = 1，undo_log 里存的是「把 count 改回 100」，并带上修改前的数据快照（用于校验）。

（D）全局锁：防脏写

  • 要解决的问题：事务 A 改了某行、还没提交，事务 B 也想改同一行——如果 B 也能改，A 回滚时会把 B 的修改一起抹掉（脏写）。
  • Seata 的解法：全局锁。A 改某行时先拿到这行的全局锁，B 想改同一行就必须等 A 提交释放锁。
  • 读隔离：默认是「读未提交」；要「读已提交」得用 SELECT ... FOR UPDATE（它会检查全局锁）。

（E）数据源代理（为什么对业务零侵入）

  • 开启后，Seata 自动把每个 DataSource 包一层代理，所有 SQL 都先经过它，自动生成 undo_log。业务代码完全无感知——这就是 AT 模式「一个注解就够」的原因。

（F）集成步骤（8 步，问细节时能报出来）

  1. Docker 启动 Seata Server（TC，8091 RPC / 7091 控制台）。
  2. 建 seata 库（global_table / branch_table / lock_table）。
  3. TC 注册到 Nacos（registry.conf）。
  4. 每个参与事务的库建 undo_log 表（jsg_trade / jsg_cart）。
  5. 各服务加 spring-cloud-starter-alibaba-seata 依赖。
  6. Nacos 公共配置里加 seata.*（事务分组、TC 地址、AT 模式）。
  7. **下单方法上加 @GlobalTransactional**。
  8. 验证：停掉 cart-service 再下单，运单应该回滚（这是最直接的验证方法，一定要说）。

（G）项目里挂在哪个方法上（要能精确说出来）

  • 全项目唯一挂 @GlobalTransactional 的地方就是这里（小程序下单链路），事务名 order-submit-tx。
  • @Transactional 和 @GlobalTransactional 是两层，要叠加使用：@Transactional 管本服务内的本地事务，@GlobalTransactional 管跨服务跨库的全局事务。

3.3.3 为什么用 AT，不用 XA 或 TCC

对比项 AT（本项目） XA TCC
一致性 最终一致（极小窗口） 强一致 最终一致
性能 高（一阶段就提交，不长时间持锁） 低（锁要持有到二阶段结束） 中
数据库要求 支持事务就行 必须支持 XA 协议 无要求
代码量 1 个注解 1 个注解 每个资源要写 3 个方法（try / confirm / cancel）
适用场景 绝大多数业务 金融、支付核心流水 调第三方 SDK、发消息等无事务资源

选型逻辑（要能讲出取舍）：

「选 AT 的核心原因是它对业务零侵入。 我只要在方法上加一个 @GlobalTransactional，其他代码一个字不用改——数据源代理自动帮我写 undo_log。

TCC 的性能上限比 AT 高，因为它不依赖数据库的回滚，而是业务自己实现 try/confirm/cancel。但代价是每个参与方都要写三个方法——对一个订单加库存的场景，你要写「预占库存 / 确认扣减 / 释放预占」，业务侵入极大，而且 cancel 要考虑各种幂等和空回滚的情况。在这个项目里不值得。

XA 的问题是锁持有时间太长——一阶段执行完不提交，锁一直拿着到二阶段结束，高并发下性能受不了。

但也要说清楚边界：AT 不是强一致，是「最终一致」，中间有一个极小窗口（阶段二回滚之前，数据是「已改但会被撤销」的状态）。如果要读这个中间状态，就得用 SELECT ... FOR UPDATE 检查全局锁。所以不是所有场景都适合强一致——我这个项目里，核心写链路（下单）用 Seata 保证一致，而通知类的事情（支付结果通知、发短信）用 MQ 做最终一致，两套方案各管各的。」

3.3.4 跨库 join 怎么办：快照冗余 + 批量查询

问题：一服务一库之后，SELECT o.*, p.name FROM orders o JOIN product p ON ... 这种 join 做不了了。

两个应对手段：

手段一：写时冗余快照（针对「历史事实」型字段）

  • 为什么可以冗余：运单是「历史事实」——下单时这个产品的名字是什么，就是什么。之后产品改了名，运单里存旧名反而是正确的（打官司的时候要用当时的价格和名字）。
  • 代价与边界（主动说）：「产品改名之后，新订单用的是新名，旧订单里还是旧名。这不是 bug，是刻意的取舍——运单记录的是『当时的交易』，不是『产品现在的状态』。但有些字段不能这么做快照——比如「门店当前是否营业」，它需要的是实时最新值，这种就必须走 Feign 实时查，不能冗余。判断标准是：这个字段是『历史事实』还是『实时状态』。」

手段二：批量查询（避免循环单条查询 —— N+1 问题）

为什么 N+1 是必须避免的：

「这是跨服务调用里最容易犯的性能错误。 单机时 N+1 只是多了 N 次数据库查询（走本地网络，快）；微服务下 N+1 变成了 N 次跨网络的 HTTP 调用——每次都要经过负载均衡、序列化、网络往返、反序列化，代价是数据库查询的几十倍。

我在多个地方都做了这个优化：运单列表、草稿列表（Feign 批量查产品）、报表统计（Feign 调 user-service 查客户数据）。统一的原则就是：一页数据只调一次下游。」

  • 顺带提：IN 子句的批量查询也要注意——如果 productIds 有几万个，IN (?, ?, ...) 会超出 SQL 参数上限或者让 SQL 变得极长。生产上要分批（比如每 1000 个一批）。

3.3.5 已知的不足（主动交代）

「有一个地方我没做：后台的『草稿转单』目前还没挂全局事务。 它和下单一样，也要同时改 cart 库（草稿标记为已转）和 trade 库（创建运单）——理论上会有和下单一样的数据撕裂风险。

为什么没做：这个功能是先做的，做的时候还没集成 Seata；后来集成 Seata 时优先覆盖了小程序下单这条用户直接接触的核心链路。

怎么修：方法上再加一个 @GlobalTransactional 就行，改动很小，是明确的优化项。我宁愿主动说出来，也不想等被问出来——因为这说明我知道哪些地方该有事务、哪些地方还没有。」

★ 一个必须讲的细节：为什么要在 afterCommit 之后发消息

「消息必须在本地事务提交成功之后再发。如果在事务里面发（@Transactional 方法体内直接发），会有两种错：

  • 事务回滚了但消息已经发出去了 → 消费者收到一条「运单已创建」的消息，去数据库一查根本查不到这个运单，只能报错或者空跑。如果消息里还带了业务数据，甚至可能造出一张不存在的运单。
  • 消息发出去了但事务还没提交 → 消费者可能比生产者的事务更早读到数据库（因为生产者的提交还没完成），读到的还是旧状态。

正确做法是 TransactionSynchronizationManager.registerSynchronization 的 afterCommit 回调里发，保证「消息发出去的时候，事务一定已经提交、数据一定能被查到」。」

两种延迟实现的对比（追问必答）

方案 怎么做 优点 缺点
TTL + 死信队列 建一个队列设 TTL，消息过期后自动转到死信队列，消费死信队列 原生支持，不用装插件 整个队列只能有一个 TTL；而且队列是 FIFO——队头阻塞：如果队头消息 TTL 是 30 分钟、后面的是 1 分钟，后面的必须等队头过期才能出来
延迟交换机插件（本项目，rabbitmq_delayed_message_exchange） 用 x-delayed-message 类型的交换机，发消息时 setDelay(毫秒) 指定 每条消息可以设不同延迟，没有队头阻塞 需要装插件（Docker 里靠自定义镜像内置解决）
  • 为什么项目选插件：因为「30 分钟关单」虽然现在只有一个延迟值，但架构上要考虑后续可能有「15 分钟催付」「2 小时自动完成」这类不同延迟的需求——插件方案不用因为需求变化就重新设计队列结构。

3.4.3 消息幂等：状态机 + 唯一键双保险

先说清楚：为什么消息一定会重复

「为了保证不丢，就必须有重试——网络抖动、消费者 ACK 丢失、RabbitMQ 重投、消费者处理完但确认时挂了……只要有重试，就一定会重复。这是分布式的铁律：消息投递的语义是「至少一次」（at-least-once），不是「恰好一次」。

所以幂等不能寄希望于『不重复』，必须由消费端自己保证『重复了也没关系』。」

第一层：状态机（业务层，挡掉绝大多数）

  • 为什么要判断两个条件（待付款 + 未支付）：「待付款」是运单状态，但这个运单可能已经支付了但状态还没更新（MQ 消息乱序到达）——所以还要看支付状态。

第二层：唯一键（数据库层，兜底并发和极端情况）

  • 同一个运单重复建支付单 → 直接插库失败，捕获异常当成「已处理」直接返回。

分工（这句话很能体现思考）

「状态机挡掉 99% 的重复消息——性能好、无副作用、语义清晰。唯一键兜住剩下的并发场景——绝对可靠，代价是会抛异常。两层配合：常态下走快路，极端情况有兜底。」

★ 一个关键细节：状态判断和更新必须在一起

  • 为什么这条重要：「先查后改」在任何并发场景下都是错的——查和改之间永远有窗口。条件更新（WHERE status = ?）把判断和修改放到一条 SQL 里，由数据库保证原子性，这是最可靠的幂等实现方式之一。而且要注意检查影响行数 —— affected == 0 说明条件不满足，业务上就是「已经处理过了」。

支付回调的幂等（同类思路）

  • 支付单状态机：0 待支付 → 1 已支付 → 3 退款中 → 4 已退款；分支 0 超时未付 → 2 已关闭。
  • 回调处理用条件更新，只允许 0 → 1：已支付过的再来直接忽略，不会重复发 MQ。这就避免了「一次支付触发两次订单状态更新」。

3.4.4 WebSocket 多实例推送：Fanout 广播

要解决什么问题

「用户在小程序里要看运单进度，我用了 WebSocket 推送。但 trade-service 是可以多实例部署的——用户 A 的 WebSocket 连接连在实例 1 上，而运单状态变化（比如门店点了发货）发生在实例 2 上。

如果实例 2 直接把消息推给『它自己管理的连接』，用户 A 永远收不到——因为他的连接不在实例 2 上。这就是漏发。」

怎么做

  • AnonymousQueue 是关键：它是一个「名字随机、排他、断开即自动删除」的队列。每个实例都有自己的一个，所以广播能被所有实例收到；实例下线时队列自动删除，不会留下垃圾。

为什么用 Fanout 而不是 Direct

  • Direct 只投给一个队列——如果服务要动态扩缩容，你没法预先知道有多少个实例、队列名字是什么。Fanout 天然适配「实例数量动态变化」的场景。
  • 这个设计的本质是「把 MQ 当成一个分布式的发布订阅总线」，解决的是「多实例之间的消息如何互通」。

「为什么不直接用 Redis 的发布订阅？」（可能的追问）

「Redis 的 Pub/Sub 也能做广播，但它不持久化——如果某个实例在发消息的那一刻正好在重启，它就连不上、消息丢了。而 MQ 有队列存储，实例恢复后能消费到积压的消息。WebSocket 推送虽然可以容忍少量丢失（用户重新打开页面会拉最新状态），但用 MQ 更稳妥。」

3.4.5 消息可靠性三层 + 死信兜底

环节 机制 配置 作用
生产者 → 交换机 Publisher Confirm publisher-confirm-type: correlated 确认消息到达了交换机（否则网络抖动会静默丢失）
交换机 → 队列 Publisher Return publisher-returns: true 路由失败（没有队列匹配 RoutingKey）时回调通知，可以重新路由或告警
队列存储 持久化 队列 durable=true + 消息 deliveryMode=2 RabbitMQ 重启后消息不丢
队列 → 消费者 手动 ACK acknowledge-mode: manual 业务处理成功才确认；失败可以重投或转死信
兜底 死信队列（DLX） 队列绑 x-dead-letter-exchange 处理不了的消息不会消失，可以人工排查/告警/补偿
  • 为什么必须是手动 ACK：默认的自动 ACK 是「消息一投出去就认为消费成功」——消费者拿到消息还没处理完就崩了，消息就永远丢了。手动 ACK 保证「业务真的成功了」才确认，消费者崩溃时消息会重新投递。
  • 什么情况会进死信：消息过期（TTL 到了）、队列满了、消费者 NACK 且不重新入队。
  • 一句话口径：「三层可靠 + 一层兜底——confirm（到交换机）、return（到队列）、持久化（不丢盘）、手动 ACK（消费成功），加 DLX 兜底。」

微信回调的三个安全细节（必须讲，这是加分点）

要解决什么问题

3.6 项目二收口问题

Q1：这个项目最大的难点是什么？

「最大的难点是「分布式事务」和「跨库之后的数据查询」这两个问题。 它们本质上是同一件事的两面——你把数据拆开了，写的时候要保证一致，读的时候要能拼回来。

  • 写：下单要同时改 cart 库和 trade 库，本地事务管不住。我用了 Seata AT——它的好处是零侵入，一个 @GlobalTransactional 注解就够，数据源代理自动写 undo_log。但选它是因为我比较过 AT、XA、TCC：XA 锁持有时间太长；TCC 要写三套方法、业务侵入太大；AT 在性能和侵入性之间是最好的平衡，代价是它是最终一致、中间有个极小窗口。
  • 读：一服务一库之后跨库 join 做不了了。我的解法是分两类处理——「历史事实」型的字段（产品名、下单时价格）用写时快照冗余，因为运单记的就是当时的交易；「实时状态」型的字段（门店是否营业）必须 Feign 实时查，不能冗余。列表页还专门做了批量查询优化，把 N+1 次调用压成 1 次。

这两件事让我理解了一句话：微服务的每一个好处，都对应着一个必须自己补上的代价。」

Q2：这个项目的不足 / 可以优化的地方？

「我列四条：

  1. 草稿转单没挂全局事务——它和下单一样要同时改两个库，但做这个功能时还没集成 Seata。修复很小（加一个注解），是明确的优化项。

第一个项目（盖楼吧）解决的是「单机怎么把性能做上去」——全部技术都围绕 Redis：缓存怎么防三个问题、秒杀怎么保证原子、Feed 流怎么设计时间线、签到怎么省空间。它让我把 Redis 这个组件用透了。

第二个项目（今日速达）解决的是「拆开之后怎么不出事」——Nacos 怎么让服务找到彼此、网关怎么做统一鉴权、跨库怎么保证一致、服务挂了怎么不雪崩。它让我理解了分布式的代价。

做第一个的时候我完全没想过一致性问题，因为一个库一个 @Transactional 就解决了。做到第二个才发现，拆开之后每件事都变复杂了。 这两个项目串起来，我对『从单体到微服务』这条路是怎么走的，有了完整的体感。」

Q4：这些项目是照着视频/教程做的吗？AI 占多少？

「我不回避。技术栈的组合方式、组件的用法，确实是从教程和官方文档学的——毕竟这些组件不可能自己发明。

但这个项目里有一些东西是我自己想清楚的：

  1. 服务拆分的边界。教程里通常是按「表」或者按「功能」拆，我按业务域拆，而且刻意没有把运单和报表拆开——因为它们共用同一套状态机，硬拆会让分布式事务到处蔓延。这是一个「不做什么」的判断。
  2. 降级策略的分类。我总结的是：写操作抛异常（沉默失败 = 数据不一致）、关键读抛异常（不能返回 null 引发 NPE）、统计查询返回空（少一行数据可以接受）。这个是按「错误的代价」来分类的，不是抄的。
  3. 跨库查询的两类处理。我把字段分成「历史事实」和「实时状态」——前者快照冗余、后者实时查。产品改名了运单里存旧名不是 bug，是正确的。 这个判断是我自己想明白的。
  4. 整套部署链路。healthcheck 控制五个依赖的启动顺序、端口只暴露网关、Seata Server 注册到 Nacos——这些是配出来的，踩过的坑我能一条条讲。

AI 的占比：前端页面 AI 帮得比较多；后端大概七成是我自己实现的——服务拆分、表设计、网关鉴权链路、Seata 集成、MQ 拓扑设计、幂等方案，这些核心设计都是我做的。AI 主要用在查 API 用法、写重复的模板代码、以及帮我看报错。我有一份开发日志记录哪些是 AI 辅助的。」

Q5：如果再做一遍，你会怎么改？

「三个优先级：

  1. 补全全局事务的覆盖——把草稿转单也用 @GlobalTransactional 包起来，让所有跨库写的链路都有一致性保证。
  2. 加服务间鉴权——现在 X-User-Id 的防伪造靠网络隔离，应该加一层内部 token 或 mTLS，把防护从「部署保证」升级成「应用保证」。
  3. 补压测——我现在的限流阈值（5/s、10/s、20/s）是估的，没有实测。要真正知道系统的瓶颈在哪，必须上压测工具看每个环节的承载能力，再据此配阈值。」
